All Code Is Slop (Except Mine) — Lauren Tan, SpaceXSI

AI Engineer · Lauren Tan ("poteto"), Grok Bot team at SpaceXSI · uploaded 14 Nov, 6:30 PM IST · 17:32
Verdict: worth watching — familiar "software factory" theme, but unusually concrete rules (ban useEffect, ban comments, lint over prose) and real numbers.
🔁 Repeat: 'software factory' — seen 22 times before. New here: she argues against jumping to a factory first; the payoff comes from deterministic guardrails in the codebase itself.
🔁 Repeat: 'AI-generated code validation' — seen 40 times before. New here: concrete use of TLA+ and Lean formal verification plus property-based UI testing (Bombadil) on a shipping desktop app.
🔁 Repeat: 'coding agents in production' — seen 85 times before. New here: hard numbers from one team (11,000 PRs a month, ~0.5% revert rate, 227 contributors).
Trust comes from the codebase, not prompts
  • 3,000 PRs in a month: She personally shipped about 3,000 pull requests to production last month, and says the engineer's job now is keeping or raising code quality while massively raising output; it took her 6 months to get there (0:40–1:59)
  • The inverse trust pyramid: Spend most effort on deterministic layers first (API design, architecture, lint rules, types, tests), then runtime and formal verification, and only a thin layer of prose (rules, skills, AGENTS.md); every correction to an agent should become a code check, not another rule line (2:03–3:31)
  • Codebase as a garden: Review load went from ~3 PRs a day in 2024 to ~300; agents copy whatever pattern they see, so workarounds, deprecated code and anti-patterns spread like weeds unless the codebase is kept pristine (repeat) (3:31–4:59)
Enforcing architecture with lint rules
  • Dune framework: Dune, their "Next.js for Electron apps", bans React useEffect in product code (only allowed inside Dune APIs), which removed that whole class of review comments (5:00–6:05)
  • Context through directories: Top-level electron-main and electron-renderer folders, with cross-imports blocked by a dependency-graph analyzer and lint rules, stop agents pulling main-thread code into the renderer and causing jank (6:06–6:50)
  • 99% of comments banned: In Cursor, agents patched an architecture clash with setTimeout / requestAnimationFrame timers and wrote comments justifying it, which hurt performance through GC churn; Grok Bot now bans almost all comments and uses lint errors that tell the agent to fix the root cause (7:04–9:40)
Verification is where the tokens go
  • Runtime verification + feature maps: Agents run the app themselves via Chrome DevTools Protocol, guided by a "feature map" (a user-facing sitemap of features) and reusable custom CLIs that cut tokens; review now means checking videos, screenshots and diagrams (9:40–10:50)
  • Formal methods: TLA+ model-checks flows like cross-device notifications, Lean proves their custom virtualization library has no flicker/jitter, and Bombadil does property-based UI testing; all have already caught real bugs (10:50–11:51)
  • 70% of tokens on verification: Citing a peer who now spends 70% of daily tokens on verification, she says the same holds for her, and introduces a "state chart" skill in her pstack plugin to visualize state machines for review (11:53–13:20)
Results
  • 11,000 PRs, 0.5% reverts: The team shipped 11,000 PRs last month, cuts a stable release about daily, had 227 contributors in October, and the revert rate held at ~0.5% while startup, typing and chat-switching got faster (13:32–15:11)
  • Auto-fuzzing releases: Each new release spins up a Cursor project that fuzzes the whole app like a user, opens fix PRs and auto-merges them; most product code no longer needs deep human review (16:00–17:20)

Did Fable 5.2 Just Build Windows 95 for a Microcontroller?

Better Stack · Andris (Better Stack) · uploaded 14 Nov, 8:15 PM IST · 17:07
Verdict: worth watching — fun, concrete demo of a frontier model doing real embedded work; skim from 7:45 if you don't care about the soldering.
🔁 Repeat: 'LLM releases / benchmarks' — seen 47 times before. New here: not a benchmark rundown but a hands-on hardware build testing Claude Fable 5.2 on a real ESP32-S3.
Building the hardware
  • The challenge: Anthropic's demo had Fable 5.2 build a laptop OS with 1,000+ subagents over 8 days; he tried an OS for an ESP32-S3 (2 cores at 240 MHz, 16 MB flash, 8 MB PSRAM, ~300 KB fast RAM) on a single Claude Max subscription (0:00–2:03)
  • VGA instead of HDMI: HDMI needs ~250 million bits/s per data line, far beyond the chip's pins, so he soldered a resistor VGA adapter (440 Ω bright bit + 1 kΩ dim bit per colour = 64 colours); the monitor rejected the standard 25.175 MHz clock until the agent switched to 26.67 MHz (2:03–6:14)
  • Input and case: Neither onboard USB-C port could host a keyboard/mouse, so he added two USB-C breakouts (data + 5 V power), and Opus designed a 3D-printed box (6:14–7:36)
How Fable worked
  • Own eyes and hands: With a JetKVM feeding the screen to Chrome and acting as keyboard/mouse, Fable also built a serial channel to dump pixel-perfect PNG screenshots and inject clicks for testing (7:45–9:14)
  • Designing around slow memory: Screen memory sits in PSRAM writable at only 35 MB/s, so the mouse pointer is painted like a hardware sprite (60 FPS, zero memory writes) and "chasing the beam" removed tearing; a full-screen copy dropped from 6.9 ms to 0.55 ms (9:14–10:31)
What Bevel OS can do
  • Desktop and apps: Windows-95-style window manager, taskbar, Alt+Tab, widget toolkit, file manager, text editor, Unix-style terminal on a 12 MB flash drive; boots in 0.7 s (target was 3 s) and drags windows at 68 FPS (10:31–12:09)
  • Snake, Doom, browser: Loadable apps include a 4.8 KB Snake and a 348 KB Doom (doomgeneric) at ~32 FPS with dithering, plus a text-only HTTPS browser over Wi-Fi using FrogFind since Google needs JavaScript (12:09–14:43)
  • Limits and totals: Wi-Fi password stored in plain text and crashing apps can reboot the system; one session of just over an hour produced ~11,000 lines of C into a 1.9 MB OS, and the hardest part was his own soldering (14:43–16:23)

Docker Desktop Has a New Competitor. It's Built in Rust

Better Stack · Josh (Better Stack) · uploaded 14 Nov, 12:15 PM IST · 7:13
Verdict: skim — short tool intro; the local domains and one-click sharing (2:24) are the interesting part.
🔁 Repeat: 'free dev tools' — seen 16 times before. New here: Kiri itself, a Rust Docker-compatible runtime not covered before.
What Kiri is
  • Claim: Kiri starts a tiny container in 22 ms, nearly 8× faster than Docker Desktop, with the same Docker commands, Compose files and Dockerfiles (0:00–0:30)
  • Runs everywhere: Small custom Linux VM on Mac, WSL2 on Windows, directly on the host on Linux; the daemon uses ~10 MB RAM and the VM shuts down after 60 s idle and boots back in ~0.1 s (0:30–1:04)
  • Drop-in setup: Installing creates a "kiri" Docker context, so it can sit beside Docker Desktop and you just switch contexts (1:12–1:45)
Features beyond speed
  • Local domains and sharing: Containers get local domain names (optional HTTPS on Mac) with no port mapping, and a Share button gives a public link to a locally running app (needs a Kiri cloud account) (2:24–3:24)
  • Why it's faster: Instead of dockerd → containerd → runc → shims, a small daemon talks to an agent in Linux that starts containers with clone3 in their own namespaces; the 10 MB figure is only the daemon, not the VM (3:24–4:30)
  • Not a clean sweep: In Kiri's own tests Colima reads bind mounts faster and OrbStack handles more new HTTP connections/s; it imports Docker Desktop/OrbStack images and offers single-node Kubernetes in ~20 s (4:30–5:49)
Caveats
  • Still beta: It's new and in beta; networking, volumes, permissions, builds and Compose edge cases make replacing Docker a big job, so try it but don't uninstall Docker (5:49–7:13)
