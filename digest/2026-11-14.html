React Server Components Weren't Worth It | Better Stack Podcast Ep. 20

Better Stack · Tanner Linsley (creator of TanStack) with hosts James and Andrew · uploaded 13 Nov, 6:30 PM IST · 1:39:37
Verdict: worth watching from 58:44 — the RSC teardown with real numbers is the fresh part; skim the Lovable/Claude story (42:18) and npm hack (1:25:03), and skip the origin story.
🔁 Repeat: 'JS/TS ecosystem' — seen 15 times before. New here: the first long interview with TanStack's creator, including why he pulled React Server Components out of tanstack.com.
🔁 Repeat: 'AI supply chain security' — seen 8 times before. New here: a first-person account of how TanStack handled its npm hack (war room, postmortem), not another general security talk.
🔁 Repeat: 'software cloning' — seen 4 times before. New here: Tanner's own "slop fork" of React (Redact) and where he draws the line between a slop fork and AI-assisted engineering.
Origins and money
  • Built at Nozzle: TanStack came out of Nozzle, an SEO data startup that tracked custom lists of 100,000+ keywords on Google; React Table was built there as the data grid, and React Query came after 3–4 years of struggling to scale Redux (1:14–4:29, 13:13–13:30)
  • No VC on purpose: Investors offered "bags and bags of money" in 2018, but he refused to build a hosting product; core maintainers keep full-time jobs elsewhere and get extra pay from TanStack's sponsorships and partnerships, and Tanner went full-time three years ago (35:48–39:04)
AI, slop PRs and slop forks
  • PRs closed on some repos: TanStack shut off PRs on a couple of projects because of AI junk and cache-poisoning attempts after its security incident; he also brushed off someone's "19 times faster" Grok rewrite of TanStack Router (19:48–21:30)
  • TanStack Charts and Redact: He designed the Charts API by hand but says "huge swaths" were implemented with AI in about two weeks; he also built Redact, an experimental React-compatible fork, in 2–3 days, and it runs tanstack.com today and saves about 30 KB of JavaScript, but he says don't use it (21:30–24:13)
  • Code is cheap, hardening isn't: He says AI-run micro-benchmarks (like a "10x faster" link that saves nanoseconds) mislead, and that mass slop-forking would "destroy open source"; small helper packages like left-pad are gone, but big libraries matter more now (25:00–30:00)
Lovable, Claude and adoption
  • Lovable and Claude switched: Lovable tried four frameworks, picked TanStack Start for all generated apps, and moved lovable.dev itself onto it; Anthropic moved the Claude web app to TanStack without telling the team, and they found out from a tweet (42:18–46:00)
  • Less training data helps: Lovable found models couldn't stick to one Next.js version because of mixed training data, while TanStack Start has only one way of doing things, so a single instruction is enough (53:00–55:00)
  • npm stats and 1.0: By his npm stats, TanStack Query is used about as much as Next.js, with a jump in 2026 he puts down mostly to Lovable; Start 1.0 has one middleware checkbox left, and TanStack AI hit release candidate the day they recorded (47:30–49:20, 50:39–52:20)
Why RSC came out
  • Extra complexity: Moving the docs' Markdown pipeline into RSC meant a separate React module graph and Vite tricks to stop bundles leaking into each other, and every later feature had to handle RSC edge cases (58:44–1:04:00)
  • 16 KB beat RSC: RSC only kept Shiki and Rehype off the client, so he had AI check how much of the Markdown spec the docs actually used (about 60%) and write custom libraries; the result cost 16 KB in total, and shipping that beat RSC's HTML payload, which became TanStack Markdown and Highlight (1:05:39–1:12:10)
  • Verdict on RSC: He calls the ROI on RSC poor: "I don't think it was worth it" (1:19:50–1:20:30)
The npm hack
  • Response: He was on vacation when it hit; about 15 maintainers were in a war room within 10–15 minutes, the first bad packages were deprecated within minutes, and security firms called it the fastest response they had seen. The postmortem was published for other libraries to follow (1:25:03–1:32:40)

Go Rewrote JSON After 15 Years... Here's What Changed.

Better Stack · Josh (Better Stack) · uploaded 13 Nov, 5:45 PM IST · 9:03
Verdict: worth watching if you write Go APIs — a short, concrete rundown of the breaking changes; otherwise skip.
What changed in encoding/json/v2
  • Nil slices and maps: v1 turns nil slices and maps into `null`, which breaks frontends that call `.map`; v2 gives `[]` and `{}` without any code changes, and an option keeps the old behaviour (0:00–0:45, 1:37–2:43)
  • Duplicate keys rejected: Given `"role":"user"` and `"role":"admin"`, v1 silently takes "admin"; v2 throws an error. He calls this a security fix, because services that pick different values can disagree on permissions. Invalid UTF-8 is also rejected now (2:43–3:37)
  • Case-sensitive fields: v2 matches struct fields case-sensitively by default, so clients sending the wrong casing can silently stop filling a field; unknown fields are still ignored unless you set `RejectUnknownMembers` (3:37–4:12)
Performance and design
  • Faster even on v1: Official benchmarks show up to 10x faster unmarshalling, and Go 1.27 moved the old `encoding/json` onto the new engine, so you get some of the speed just by upgrading. Marshalling is about the same (4:12–4:59, 6:45–7:13)
  • Two layers: `jsontext` handles syntax, tokens and streaming, and `json/v2` maps to Go values, with new `MarshalWrite` / `UnmarshalRead` and per-call options (4:59–5:32)
  • vs Sonic and friends: Sonic (JIT + SIMD), go-json and json-iterator can still beat v2 on some workloads; if you're on Sonic and it's faster, keep it, but benchmark v2 for new projects before adding a dependency (5:32–6:20)
Migrating
  • Gotchas: `omitempty` behaves differently, map keys are no longer sorted (exact-output tests may fail), and `time.Duration` has no default format, so you get an error until you choose one (6:20–7:13)
  • Path: Upgrade to 1.27 first, then move endpoints one at a time, starting from `DefaultOptionsV1`; the `jsonsplit` tool runs v1 and v2 side by side, reports the differences but still returns v1's result, and can sample only some calls (7:13–9:02)
