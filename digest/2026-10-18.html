An AI Agent Got Its User Banned From Resy — Keycard, JPMorgan Chase & AAuth

AI Engineer · Allie Howe (Keycard, moderator), Ian Livingstone (Keycard CEO), Michael Davis (JPMorgan Chase), Dick Hardt (AAuth, OAuth co-creator) · uploaded 18 Oct, 4:30 AM IST · 43:25
Verdict: skim from (7:00): the mission, Resy-budget and brain-vs-hands sections are the substance; the rest is panel generalities.
🔁 Repeat: 'agent security' — seen 18 times before. New here: intent-based runtime authorization, and AAuth's "mission" and "budget" primitives as a protocol rather than a vendor feature.
🔁 Repeat: 'agent governance' — seen 6 times before. New here: a bank security architect's view on "know your agent" alongside know-your-customer.
Why OAuth doesn't fit agents
  • Security systems built for humans: Enterprises, especially regulated ones, put security first, and their identity stacks were designed for humans making decisions and deterministic software, not a model that retries until it finds a way (2:00–4:00)
  • Scopes are too coarse: You don't know in advance what an agent will need, so mapping existing OAuth scopes onto agents is far too coarse; for example, Notion's MCP server lets you fetch a page but not just one database on that page (4:00–6:00)
  • Intent as the memo field: One panelist compares intent to the memo line on a cheque: the cheque still has hard limits (amount, payee, date), but the memo explains the purpose, which makes runtime decisions and debugging easier (6:00–7:00)
Missions, budgets and the Resy incident
  • AAuth missions: A mission is the big-picture goal the agent works toward on behalf of a person or organization; every decision is made in its context and the mission ID tracks through everything for auditing (7:00–11:00)
  • A separate supervisor: The AAuth view is a supervising agent that can't do any work itself but decides what the worker agent is allowed to do (11:00–12:00)
  • The Resy ban: An agent trying to book a restaurant made 200 API calls an hour and got the user's Resy account banned; AAuth answers this with budgets, so a token expires either on time or when its resource budget runs out (25:00–27:00)
  • Brain vs hands: Keep credentials and enforcement in a deterministic layer outside the model, the pattern Anthropic and OpenAI are following, and remove tools dynamically, e.g. disable web egress while an email-writing step is in progress (28:00–31:00)
Production reality and P(doom)
  • Intent saves tokens too: Telling the agent what it shouldn't do nudges it onto a paved path, so it wastes fewer tokens or stops and says it can't do the task (31:00–32:00)
  • Lessons from robotics: Most authorization today is a single binary decision; Davis wants context-rich, short-lived decisions that also weigh environment signals like location, time of day or which browser an admin is using (35:00–38:00)
  • Audit log outside the agent: You still need a record of who told the agent to do what and for what purpose, kept outside the agent itself (38:00–39:00)
  • P(doom): One panelist worries most about insider threats and irresponsible actors causing disaster-scale harm; another puts the odds at "approaching asymptotically zero" because incentives and liability frameworks still apply (39:00–43:20)

How to Know If Your AI Agent Is Any Good: Evals With Phoenix & Claude — Laurie Voss, Arize AI

AI Engineer · Laurie Voss (Head of DevRel, Arize AI; npm co-founder) · uploaded 18 Oct, 12:30 AM IST · 1:56:13
Verdict: worth watching, or skim from (43:21) if you already trace your agents: the judge-validation and experiment sections are the best evals material in a while.
🔁 Repeat: 'evals for agents' — seen 29 times before. New here: a full worked loop on one agent with real numbers, including testing the judge itself against human labels and proving a model upgrade with evidence.
🔁 Repeat: 'agent observability' — seen 17 times before. Tracing setup with Phoenix is standard; the error-analysis-by-coding-agent part is the fresher bit.
The mental model
  • Traces are logs, evals are tests: Evals are tests run on traces for outputs that are never the same twice; "looks good to me" on three tries isn't a test suite and doesn't catch regressions (4:57–8:00)
  • Three kinds of eval: Code evals are instant and free (formats, required fields, banned phrases), LLM judges handle meaning but can be confidently wrong, and humans catch unknown failures and check the judges (8:30–11:57)
  • Agents fail in cascades: A financial agent asked about Tesla can find the 18th-century inventor and write a perfectly formatted, wrong report; in one airline benchmark Claude upgraded a passenger to first class to change seats, then downgraded them back (11:57–14:00)
Reading traces: the 116% bug
  • Setup: A Claude Agent SDK financial analyst on Claude Haiku 4.5 with a research turn and a writing turn, traced with Phoenix in about five lines of TypeScript (16:32–22:00)
  • The bug: For "yo is Tesla a buy right now", it merged two unrelated web results into 50% buy, 52.6% hold and 13.1% sell, about 116% of analysts, and stated it confidently (43:21–45:00)
  • Other failures found: An ambiguous prompt plus no-permission mode made it keep trying to write the report to a file, and many reports never said buy, sell or hold (28:00–31:00)
Writing evals
  • Code eval first: A ticker-mention check runs instantly and caught the Amazon query where the agent wrote only about AWS (50:36–55:00)
  • Correctness eval failed everything: Phoenix's built-in correctness judge (on Sonnet 5.5) marked every report wrong because October stock prices are after Claude's knowledge cutoff; faithfulness against the search results was the right choice and flagged 14 of 16 reports with useful explanations (1:00:30–1:07:00)
  • Custom actionability judge: A five-part rubric whose criteria come from your own error analysis; 5 of 16 reports passed, and simply wrapping inputs in XML tags flipped results, so treat eval prompts as code (1:10:41–1:24:00)
Trusting the judge and shipping
  • Test the judge: Label reports yourself, split 75/25 into dev and test, and measure the judge's precision and recall like a classifier; humans disagree too, so the bar is "better than another human" (1:24:45–1:38:00)
  • Experiments prove fixes: One prompt line raised actionability from 5/16 to 48/48 across three runs, but faithfulness only went from 2/16 to 3/48, so the agent still invents numbers (1:38:55–1:47:00)
  • Haiku 5.5 upgrade: Faithfulness more than tripled but stayed poor, cost rose about 4×, and it got "consistent" by answering hold 41 of 45 times (1:48:30–1:50:55)
  • Evals in CI: `npm test` gates on the ticker check as a guardrail and average actionability of 0.8 or better as a target (1:50:55–1:55:25)

Stop Chatting With Spreadsheets — Francesco Galletta & Felippe Felisola Caso, Monzo

AI Engineer · Francesco Galletta & Felippe Felisola Caso (Monzo, speaking for themselves) · uploaded 17 Oct, 7:30 PM IST · 1:50:34
Verdict: skim from (35:48): the branching-plan and math-in-code sections plus the evidence labels are the takeaways; much of the runtime is live setup and audience back-and-forth.
🔁 Repeat: 'harness engineering' — seen 20 times before. New here: five trust principles applied to a finance harness, with a branching plan instead of one linear chat.
🔁 Repeat: 'human-in-the-loop review' — seen 8 times before. New here: "few gates with very high signal", reviewing tasks rather than individual changes.
Trust, not speed
  • Impact over token-maxing: Their Monzo team adopts AI deliberately for concrete business value, not to spend tokens (2:54–4:22)
  • The five principles: Shared domain, consistency, evidence, accountability and verification, each building on the last (8:45–12:13)
  • The use case: Paying for a wedding in three payments with fixed costs (DJ, flowers) and an unknown guest count at about 150 per seat; the harness keeps asking questions instead of going "yes-man" (25:59–30:42)
Consistency and evidence
  • Branches, not one long chat: The plan becomes a decision tree you can edit node by node, because long linear chats fall apart when one stray sentence derails the analysis (35:48–36:48)
  • Math belongs in code: Deterministic pieces become tested code and versioned libraries the agent calls, not arithmetic "in the model's head" that gets reinvented every session (36:48–45:00)
  • Label every input: Chat thoughts are interpretations, agent memory is an assumption, a bank statement is a fact; the "master file" story shows how hidden assumptions break analyses (59:00–1:01:00)
Accountability and verification
  • Agents face no consequences, you do: Design a few high-signal gates for real judgment calls rather than approving every change (1:06:42–1:12:00)
  • Challenge branches: A separate reviewer agent challenges the plan and its result merges back in, or you dismiss it; golden examples alone carry your own selection bias, so add outside reference points (1:24:00–1:32:00)
  • Harness vs skills (Q&A): Skills work about 99% of the time, but a user-level CLAUDE.md can contradict them; build a dedicated harness when reproducibility matters, and don't over-sharpen the axe (1:38:11–1:46:40)

The AI Bill Is Too Damn High: Tokenomics 101 — Eugene Cheah, Featherless AI

AI Engineer · Eugene Cheah (CEO, Featherless AI) · uploaded 17 Oct, 2:30 PM IST · 55:25
Verdict: worth watching if you pay a token bill; Moves 2 to 4 9:27–44:27 are the dense part.
🔁 Repeat: 'open source / local models' — seen 40 times before. New here: concrete right-sizing numbers from an inference vendor serving customers up to 2 trillion tokens a day.
🔁 Repeat: 'inference / serving' — seen 28 times before. New here: the "2× speed costs 3× the money" rule with real throughput figures.
🔁 Repeat: 'AI ROI measurement' — seen 4 times before. New here: "tokens are not work done" and the slop-grenade anti-pattern.
Move 1: measure
  • Stop sharing one API key: Split keys by department and use case so you can see who spends what; he calls measuring the biggest ROI step (3:23–9:00)
  • Two opposite workloads: Agentic work (one team of 5 devs averaged 8 agents running continuously) vs high-volume process work like content filtering and OCR; that team moved background agents to run overnight (5:12–9:27)
Move 2: right-size models
  • Open models catch up: Kimi K3 beat Opus on public UI-design benchmarks before Opus 5.5, and DeepSeek-V4 Flash is popular across workloads; classifiers are about 10× cheaper where you don't need a chat reply (11:00–15:00)
  • Plan big, build cheap: Use a frontier model to plan and review and a cheap one like Gemini 5.3 Flash for workers; teams with loose budgets never switch models, teams with tiny ones abandon the smart model entirely (15:00–18:00)
  • Model labels, not names: Give departments labels you control (one team was still running Llama 2 models); a telco went from 250k to 7.6k a month, and AT&T fine-tuned down to 27B and 7B models (19:27–25:00)
Moves 3 and 4: buy capacity, fix process
  • Speed is expensive: Every 2× in speed costs about 3×; one server did 112 tokens/s on a single request, while 16 parallel requests ran at about half the speed for about 10× the total throughput, so don't run background jobs at 120 tokens/s (30:07–32:22)
  • Tokens are not work done: Reports show only 6–7% productivity gains; spamming agents creates duplicate work and review bottlenecks, and "slop grenades" dump AI output on others, so people must own what they hand over (34:32–44:27)
  • Q&A: A prompt-tuned Qwen 27B beat most 27B fine-tunes on a benchmark, golden traces get heavier weight in SFT, and turn-based auto-routing should stick to 2–3 models or caching breaks (44:27–55:00)

Memory-Aware Agent Harnesses for Anti-Money Laundering — Nacho Martinez, Oracle

AI Engineer · Nacho Martinez (AI developer advocate, Oracle) · uploaded 17 Oct, 12:30 PM IST · 51:49
Verdict: skim from (13:21) to about (26:40) for the files-vs-databases and skillbox ideas; the rest is well-covered harness/memory ground plus workshop setup.
🔁 Repeat: 'harness engineering' — seen 20 times before. Mostly the same "harness matters more than the model" argument.
🔁 Repeat: 'context engineering' — seen 14 times before. Summarization vs compaction and context rot are familiar.
🔁 Repeat: 'agent memory' — seen 13 times before. The short-term vs episodic/procedural/semantic split is familiar.
🔁 Repeat: 'agent skills' — seen 7 times before. New here: vector-retrieving skills and tools (a "skillbox") instead of loading them all.
The stack (repeat-heavy)
  • Use case: An always-on agent for a mid-sized bank that flags suspicious transactions, like $1M deposited and then $50,000 ATM withdrawals for three days, and writes findings for a human to review (repeat) (4:57–5:57)
  • Harness over model: You can't change the frontier model, but changing the harness alone makes the same model better or worse (repeat) (11:06–13:21)
  • Files vs databases: Worktrees are a workaround for multiple agents writing the same files; ACID databases solved that 30 years ago (13:21–15:56)
  • Context rot: Models solve problems more accurately at zero tokens than with 256K already in context, even with 1M limits (repeat) (18:00–19:46)
Toolbox, skillbox and continual learning
  • Vectorize skills and tools: With about 100 skills at 3,000–5,000 tokens each, tools and skills can be over half the context; embed them and retrieve the top 3 per request (20:51–22:30)
  • Skill distillation: Turn successful past runs into reusable skills the agent finds by semantic search, so a frozen model improves through its data layer (22:30–26:10)
  • Lean harness: His harness starts at about 6,000 tokens per request vs 30,000–40,000 for others, and a semantic cache cuts costs 4–5× (36:00–39:00)
Q&A
  • Keep memory simple: Start with just short-term and long-term and promote what's worth keeping; use MCP for pre-built, proven SQL queries rather than dynamic ones, and hybrid search (embeddings plus keyword, RRF) for retrieval (40:49–47:39)

The Internets Master Key Just Changed

Better Stack · uploaded 17 Oct, 11:30 AM IST · 5:55
Verdict: worth watching: a short, concrete explainer, and practical if anything at home stopped resolving last week.
How DNS gets faked
  • No proof in original DNS: A resolver tags each query with a random ID and accepts any answer with a matching ID; there are only about 65,000 IDs, so an attacker flooding fake answers needs about 32,000 guesses on average to poison the cache (0:56–2:11)
  • 2008 and DNSSEC: A researcher chained these weaknesses in 2008 and DNS software everywhere was patched; the long-term fix, DNSSEC (written in 2005), signs each step of the root to .com to example.com chain (2:11–3:06)
The root key and the rollover
  • The key nobody can know: The root's secret key only signs the root's own key list and leaves the vault a few times a year; on 11 October the root switched from the 2017 key to the 2024 one (key 38696) (2:40–3:38)
  • Inside Culpeper: The key sits seven layers deep in a Virginia facility; the machine needs 3 of 7 crypto officers' USB keys (from places like Sweden, Zimbabwe, Chile and Sri Lanka, none working for ICANN), and the 2024 key was generated live on 26 April 2024 in about half a second (3:38–5:15)
Who is protected
  • Low adoption, easy fix: Only about 5% of .com names are signed and about 41% of users sit behind a validating resolver; if your internet broke around 11 October, update your router or system so it picks up the new key (5:15–5:54)
