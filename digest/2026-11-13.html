Rethinking Claude Code Best Practices — Lydia Hallie, Anthropic

AI Engineer · Lydia Hallie, Anthropic (Claude Code team) · uploaded 12 Nov, 8:56 AM IST · 17:32
Verdict: worth watching — the most practical Claude Code setup guide in a while, especially the sandbox, hook exit-code and review-tier details.
🔁 Repeat: 'coding agents in production' — seen 83 times before. New here: Anthropic's own updated Claude Code defaults for the newest models, straight from the Claude Code team.
🔁 Repeat: 'sandboxes for agents' — seen 27 times before. New here: a clear explanation of why deny rules alone can't stop a compromised `npm test` dependency, and how the OS-level sandbox closes that gap.
🔁 Repeat: 'human-in-the-loop review' — seen 47 times before. New here: Anthropic's risk-tiered review (docs need no human, normal changes one reviewer, risky ones two).

She re-recorded the talk at home after technical problems on stage, so it's a screen recording with slides.

Why the old habits now hurt
  • From one session to dozens: Earlier this year sessions with Opus 4.5 stopped early and needed constant correcting; now Anthropic engineers run dozens of hours-long sessions at once. Anthropic went from about 2,500 changes a day in May to over 30,000 a day in September (0:30–2:00)
  • Trim your CLAUDE.md: "IMPORTANT!"-style shouting and notes on your stack or where to look now push newer models off track and cause extra tool calls. Keep only what Claude can't see in the code, like a legacy service that isn't referenced anywhere. A doctor prompt-audit command checks your CLAUDE.md and skills against the current model (3:00–4:00)
Keeping long unattended sessions safe
  • Auto mode, configured in plain English: Auto mode (the default since August) runs a classifier on anything beyond reading or editing files; you can tell it in plain English which repos, buckets and domains you trust. In Anthropic's August study only about 14% of people caught a clearly dangerous command, while auto mode blocked 89%, so roughly one in ten still got through (4:00–6:00)
  • Deny rules still matter: A deny rule is checked before the classifier ever sees the call, so use one for anything you can't undo, such as reading `.env`. The test she gives: if Claude gets it wrong once, can you take it back? (6:00–7:00) (repeat)
  • Sandbox the side effects: A deny rule only sees `npm test`, not a compromised dependency inside it reading `.env` or SSH keys. Turning on the sandbox hands the same rules to the operating system, which also covers child processes and blocks unapproved hosts, though MCP servers and hooks still run outside it (7:00–9:30)
  • Cloud sessions: Running in Claude's cloud gives each session a fresh machine and repo copy with no `.env`, SSH keys or GitHub token, network secrets that are never sent to the model, and network access limited to package registries and GitHub by default. Commit deny rules to the repo so they still catch force-pushes or secrets in commits (9:30–11:00)
Verification instead of watching
  • Checkpoints and hooks: The same "move auth to a new API" prompt can produce three plausible but different results, so define pass/fail checkpoints. For guaranteed checks use hooks: lint on every edit, run the changed area's tests when a task is marked done, the full suite at session end. Hook scripts must exit with code 2, because exit code 1 lets the task be marked complete anyway (11:00–13:30)
  • CI and risk-based review: CI with auto-fix lets Claude repair failing checks, and merge-when-ready can merge once checks pass. At Anthropic every PR is first reviewed by a separate Claude with fresh context; docs and copy changes need no person, ordinary changes one reviewer, risky ones two (14:00–15:00)
  • One orchestrator session: Claude Code projects (in beta) let one main session split the work and launch and verify sub-sessions, with context handled automatically. She suggests Fable 5.2 for the orchestrator and Opus 5.5 for the worker threads. Her advice: hand Claude one task much bigger than usual and see where you still get pulled back in (15:00–17:30)

Theo Just Open-Sourced the Skills He Uses to Ship Code

Better Stack · Josh (Better Stack) reviewing Theo's tstack · uploaded 12 Nov, 5:45 PM IST · 8:05
Verdict: skim from 2:00 — a quick look at the demo and the Council idea is enough; the rest is install steps and general caveats.
🔁 Repeat: 'agent skills' — seen 29 times before. New here: a skill pack aimed at everything after the code is written (tests, PRs, CI, merging) rather than writing code.
🔁 Repeat: 'AI-generated code validation' — seen 39 times before. New here: the Council skill, where Claude, GPT and Gemini review the same change in rounds.
What tstack is
  • Nine skills for shipping: tstack is nine instruction files for Claude Code and Codex covering testing, multi-model review, opening PRs, fixing CI failures, taking over unfinished PRs and even merging (0:00–1:30)
  • Setup: Clone it and copy the skills into your Claude Code or Codex skills folder. It needs an authenticated GitHub CLI and Python 3 for the PR watcher, and the review skills need access to other providers' models (he uses T3 Code's delegation tools) (1:19–1:58)
The demo
  • Full Stop on a bug fix: Typing "full stop" first tries to prove the fix works (reproduce the bug, run tests), then runs Sol Loop to have another model review it, then opens a PR whose description starts with the problem and how it was tested rather than a file list (2:00–3:15)
  • Babysit PR: After opening the PR it keeps watching CI and review comments, makes small fixes and re-verifies, but Full Stop never merges; Full Send runs the same chain and merges automatically once required checks and reviews pass (3:15–4:25)
  • Council, Takeover, Modernize: Council has three models from different providers review the code over several rounds until they agree; Takeover picks up a PR another agent abandoned; Modernize rebases an old PR and judges whether it's still needed (4:30–5:30)
Catches
  • Not plug and play: Council and Sol Loop need extra model access, and the skills call each other (Full Stop calls Full Send, which calls others), so installing one alone breaks. They're still just instructions to an agent, so you still need permissions, real tests and branch protection (6:00–7:00)
  • How to start: Try File PR and Babysit PR first, then Full Stop; consider Full Send only later and only for small, low-risk changes, and customize the skills to your own workflow (7:00–7:50)
