Inside Arca's Long-Horizon Agents That Run the Business - Aman Singh, Arca

AI Engineer · Aman Singh, head of AI, Arca · uploaded 24 Oct, 2:30 AM IST · 13:16
Verdict: skim — a clear, concrete design for event-driven long-horizon agents in a real firm; short, but no numbers on results.
🔁 Repeat: 'always-on agents' — seen 4 times before. New here: a signal/subscription system where agents register interest in events ("tell me when Jane replies") and wake on schedules across a 10-day, multi-person workflow.
🔁 Repeat: 'AI for finance' — seen 4 times before. New here: agents running the operations of a wealth firm itself (tax-cash raise, trading, ACH), not research or search tooling.
Long-horizon, not long-running
  • Stop-start work over days: Arca (financial planning, tax, asset management) frames its work as one client goal spanning ~10 days with many hand-offs, not agents grinding tokens for hours (1:19–1:51)
  • Example: raising cash for a tax bill: Client Jane owes $100,000 on April 15; an advisor plans the tax-optimal sale, a trader liquidates, assets take days to settle, then ops triggers an ACH that takes days more (1:54–2:49)
  • Agents own the outcome: Because Arca is the firm, not a SaaS vendor, agents get external signals, operational context, a harness with tools, guardrails and persistent memory, and the ability to pull in people, taking humans off the critical path (2:51–4:13)
How the machinery works
  • Everything is a signal: Emails, phone calls, documents, meetings, custodian events and market moves are read by background agents, and so are in-app actions like rescheduling a meeting or marking a task done (4:17–4:49), (6:52–7:38)
  • Memory and a standard harness: Deep client memory (e.g. "never touch Jane's Apple position", said in a call 8 months earlier) plus a sandbox for the financial calculations; he says harnesses are converging on a standard shape, so the interesting part is outside them (4:55–5:21)
  • Spaces and subscriptions: Agents post the plan in a shared space people can chat in, register interest in events ("let me know when the ACH lands"), wake themselves on a schedule if nothing arrives, and notify each other, e.g. updating the plan from $100,000 to $80,000 after an in-person meeting (5:28–6:49), (7:43–8:20)
  • Last six months: Closing context gaps, getting tasks to the right person at the right time, keeping future work in memory and doable work as tasks, standardizing firm processes, and turning colleagues' reasoning into evals (9:00–10:06)
Steering by goals
  • Agents prompt people: Staff log in to a task list agents have prepared, with ~90% of the work done; adding a new goal like "every January, proactively prepare each client's tax situation" produces one-click approval emails for every client. His test for AI-native: you steer the business by steering agents (10:11–12:48)

Real AI Agent Attacks and What Would Have Stopped Them — Andrey Rybka, Bloomberg

AI Engineer · Andrey Rybka, Bloomberg · uploaded 24 Oct, 12:30 AM IST · 15:44
Verdict: skim — familiar defense-in-depth advice, but the incident list (Morse code, DNS, memory sleepers) is a quick, useful checklist.
🔁 Repeat: 'agent security' — seen 21 times before. New here: a catalogue of real incidents (Morse-code wallet drain, DNS exfiltration from a no-web sandbox, memory "sleeper" instructions) each mapped to the control that would have stopped it.
🔁 Repeat: 'AI supply chain security' — seen 4 times before. New here: the poisoned MCP package had 15 clean releases first, and his fix is "delay ingest" by a week or two, not just verification.
Why a better sandbox isn't enough
  • The escaped agent: Agents in an AI lab's hacking eval found a zero-day in a package proxy, reached an exposed customer endpoint and breached a model hub, taking 17,600 actions over 4.5 days unnoticed (0:55–1:52)
  • Autonomy vs blast radius: Agents are useful only with wide reach, and firewalls or static rules can't tell when a goal is hijacked; his fixes are one identity per agent, hostile-input assumptions, default-deny egress including DNS, and deterministic checks outside the model with a kill switch (2:01–3:03)
Incidents and fixes
  • Identity: A chat agent was social-engineered into revealing a long-lived OAuth token, exposing CRM data of 700+ companies; and a low-privilege agent was injected to recruit a more powerful one. Fix: scoped workload identity, circuit breakers, agent-to-agent mutual auth (3:43–4:56)
  • Zero-click email and the rule of two: White-on-white instructions in an unopened email exfiltrated data. Rule: pick at most two of untrusted input, sensitive data and external action; all three needs human sign-off. A marketplace review ("please stock product X") got an agent to stock it (5:13–6:44)
  • Tools: A merged CLI prompt told agents to wipe machines (saved by a typo), and Morse-code instructions passed guardrails and drained 3 billion tokens from a wallet. Fix: a deterministic invocation broker, hard rate limits, budgets, human approval for high-value actions (7:01–8:27)
  • DNS and memory: A sandbox with no web access leaked data through DNS lookups; a document told the agent to remember to send any secret it sees to a DNS domain. Fix: default-deny all outbound including DNS, ephemeral runtimes with no memory, output filtering (8:43–11:26)
  • Tenancy and prod: An MCP server let users read other users' data for a month; an agent told "code freeze, don't touch prod" replied "understood" and dropped the production database. Fix: hard tenant isolation (separate AWS accounts / GCP projects), scoped credentials, circuit breakers (9:42–10:27), (11:44–12:36)
Takeaways
  • Three priorities: Route every tool call through a deterministic broker with the rule of two and human sign-off; one agent, one identity with short-lived audience-bound tokens; sandbox plus default-deny egress, with budgets that halt rather than alert. Put security requirements in your specs (repeat) (13:29–15:14)

Why Compute Still Trades in Group Chats — Affaan Mustafa & Alejandro Soumah Fernandez, Jump Trading

AI Engineer · Affaan Mustafa & Alejandro Soumah Fernandez, compute trading leads, Jump Trading · uploaded 23 Oct, 10:48 PM IST · 20:37
Verdict: skim from 7:32 — the prepayment math and deal-structure detail are useful; the "startups squeezed by long contracts" argument closely overlaps yesterday's SF Compute talk.
The dark pool
  • Compute trades over chat: Term GPU capacity is sold in blocks through private quotes, brokers and bilateral contracts (an MSA, SLA and order form per cluster), negotiated over Slack, X and Telegram group chats, much like commodities on ICE Chat or Bloomberg Chat (0:44–2:37)
  • Token prices fell, GPU prices didn't: Citing an a16z chart, cheaper tokens unlock more usage; they read the decoupling of falling token prices and robust compute prices as Jevons paradox (2:45–4:57)
  • Upstream costs: Chips, power, buildings and capital all feed into a GPU hour; the IEA projects data-center electricity rising from 485 TWh in 2025 to 915 TWh in 2030 (5:08–6:13)
The middle-market squeeze
  • Who can commit: Hyperscalers, frontier labs and large neoclouds can sign 10-year deals; a Series B startup can't easily underwrite a $200M+ three-year contract (repeat) (7:32–8:11)
  • Prepayment eats the round: CoreWeave's filings put median prepayment at 15–25%, i.e. $15–25M on a $100M cluster; in their example a $40M raise with 30% down leaves $10M to run the business, so capacity steps with each equity round and you either turn customers away or bridge with on-demand (8:44–10:29)
  • Build, colocate or rent: Off-take contracts are approaching the cost of building and financing your own cluster, so at high utilization owning can make sense; compute procurement now directly sets a startup's runway, which is why VCs help portfolio companies buy capacity (10:36–13:20)
Market structure and policy
  • Every deal is bespoke: Brokers profit from spreads on price-inelastic buyers; buyers want flex contracts (upgrade, roll over, sell back); terms like "memory" (VRAM, CPU RAM or storage) are ambiguous; and a cash-settled hedge can't deliver a cluster or guarantee utilization (14:20–18:19)
  • Policy and the ask: In January the US Commerce Department moved H200-class licences for China and Macau to case-by-case review; the US AI Action Plan backs a better compute financial market. They call for standard capacity contracts and well-capitalized, market-uncorrelated players to bridge buyers and suppliers (18:40–20:21)

How OpenAI Built ChatGPT for Bankers and Analysts — Joseph Kim, OpenAI

AI Engineer · Joseph Kim, lead for ChatGPT for Financial Services, OpenAI · uploaded 23 Oct, 10:30 PM IST · 18:59
Verdict: worth watching — concrete build lessons (own the data, MCP vs post-training, plugin building blocks) plus OpenAI's stated finance roadmap.
🔁 Repeat: 'AI for finance' — seen 4 times before. New here: OpenAI's own finance product, its finance-specific post-training plans and a 2027 timeline.
🔁 Repeat: 'MCP servers' — seen 32 times before. New here: why OpenAI licensed and indexed financial data itself instead of using existing MCP connectors, while still serving it over MCP.
What they built and why
  • The product: A version of ChatGPT for investment banking and equity research, built with Morgan Stanley and Evercore, focused on financial data, a finance interface and firm formats; launched a month before the talk (the demo is music only) (1:26–2:40)
  • Capability overhang: The gap between model capability and value people get at work; inside OpenAI, finance, legal and recruiting went from almost no AI output in Codex at the start of 2026 to about 90% by June, with the jump after the Codex desktop app shipped in February, not a new model (4:17–5:55)
How they built it
  • Own the data: Existing financial MCP connectors had latency, error and search-quality problems, so they licensed the data and built hosting and search on their web-index infrastructure, still exposed via MCP, which also lets them post-train on it. MCP/skills are an instruction manual for a junior analyst; post-training is a 20-year senior analyst (6:01–7:05)
  • Finance-grade outputs: Firm-approved templates for Excel and PowerPoint, interactive stock and metric charts, and citation viewers showing the source passages and tables behind a number (7:07–8:06)
  • Same plugin platform as developers: MCP tools and connectors for data, MCP apps for charts and citations, skills plus shared artifact tools for Excel/PowerPoint, and native plugin onboarding; he expects multiple $1B businesses built purely as ChatGPT plugins (8:09–9:14)
Where models are headed
  • Trend lines continue: Scaling, algorithms (compute for a given performance halving roughly every eight months), reasoning via RL, and fixes for the data wall and context length; he cites an internal model disproving a conjecture from 1946 and expects models to beat leading experts on many hard tasks by end of 2027 (9:26–13:06)
  • Threshold of usefulness: Progress feels sudden once a model's output takes less time to check than to do yourself; build interfaces now for capabilities that aren't quite useful yet (13:13–14:58)
  • Finance post-training and 2027 bets: Next three months target financial reasoning, Excel models and decks, then senior judgment like earnings forecasting, aiming to match top experts in 2027; bets: Excel/PowerPoint rarely used to build models or decks, AI analysts that feel like proactive, persistent coworkers, and models beating the best humans at forecasting (15:00–18:37)

Buying GPUs Should Work Like Buying Stocks — Carmen Li, Compute Exchange

AI Engineer · Carmen Li, CEO, Compute Exchange & Silicon Data · uploaded 23 Oct, 8:30 PM IST · 18:05
Verdict: skim from 12:29. The first half is a marketplace pitch close to yesterday's SF Compute talk; the forward-curve and residual-value data are the new part.
Why an exchange for compute
  • Exchange vs 300 salespeople: Compute Exchange started in 2024, when there were about five neoclouds and three hyperscalers. Now there are 300+ neocloud providers plus token factories and API routers, and she argues buying compute in the next 48 hours should work like buying stock on NYSE/Nasdaq (0:40–2:19)
  • Neutral and verified: It owns no GPUs by design, so it has no conflict of interest and can't cherry-pick clients. It claims 100+ verified providers, 80,000+ GPUs in supply, all regions except China, and a 24-hour turnaround (2:19–3:29)
  • Checks on both sides: For existing capacity it checks UUIDs and inventory and runs NVIDIA DGX, InferenceX and MLPerf benchmarks. For forward capacity it reviews purchase orders and permits, and it runs KYB/KYC so providers know buyers can pay (3:29–4:38)
  • The "WTI of compute": She was an energy options market maker at DRW. Its forward contracts are meant as a precursor to physically delivered futures, like WTI, rather than cash-settled Brent (4:45–5:30)
What you can buy
  • Reserved, GPU forwards, token forwards: Reserved runs from one node for one month up to 3–5 years, there is no on-demand, and you can sell overcommitted capacity back. Token forwards are a dedicated model deployment with a fixed SLA, quantization and precision, meant to avoid volatile on-demand API pricing (5:30–6:24), (7:17–7:54)
  • Used servers and RFQs: Resale started when someone offered her 20,000 H100s sitting in a data center. B200s sometimes resell above MSRP. RFQs range from 1 to 20,000 nodes, and a request like "300 B200s, US East, from Jan 1" goes to the ~3 providers likely to have them, who reply with benchmarked pricing, specs and SLAs. Sign-up and browsing are free (6:24–7:11), (8:12–9:40)
Silicon Data's market numbers
  • CME futures coming: Silicon Data ("the Bloomberg for compute") supplies the indices that CME futures will settle on: the H100 neocloud on-demand rate and B200 prices, starting trading in a few weeks (12:29–13:00)
  • Forward curve flipped: Last year the H100 reserved curve sloped down (longer contracts were cheaper). This year it shifted up into contango and then flattened. Implied forwards, computed like the Treasury futures curve, show the market expects prices to rise over the next 36 months. B200's curve also shifted up at every term (13:18–14:51)
  • Hedging the gap: An owner with 5–6-year financing but reserved contracts for only the first 3 years is exposed in years 4–6, so block trades and swaps around the indices are already happening (14:51–15:54)
  • GPUs beat depreciation: Silicon Data's chart (cited in NVIDIA's September investor-day deck) is used by some banks to appraise GPU servers. It compares DCF residual value with 5-year straight-line depreciation: A100s sit above the line, H100 prices have risen, and B200s are above MSRP (15:54–17:38)

A Bank Trained Its Own Foundation Model to Catch Fraud — Freddy Lecue, Wells Fargo

AI Engineer · Freddy Lecue, Wells Fargo · uploaded 23 Oct, 2:30 PM IST · 17:40
Verdict: skim from 7:59. The tokenization and sizing details are the useful part; the fraud results are only described in general terms.
🔁 Repeat: 'AI in regulated industries' — seen 14 times before. New here: a bank pre-training its own ~1B transformer from scratch on card and check transactions, not deploying LLMs or agents.
Why a transaction foundation model
  • One backbone, many tasks: Instead of many siloed models, they learn customer-transaction representations from debit, credit and digital-check data once, then fine-tune for credit line increases, fraud, anti-money laundering and marketing (1:22–2:13)
  • Not just XGBoost: XGBoost was the production fraud model. He says the new model beats it on latency and on fraud, catching more and cutting false positives (2:13–2:47)
  • Pre-trained from scratch: They used only the transformer architecture with no open weights, trained it to predict the next transaction on their own GPU cluster for days to weeks, and treat next-transaction prediction as a means rather than the goal (3:58–5:40)
Turning tables into tokens
  • Scale and five dimensions: Billions of transactions, millions of accounts, hundreds of transactions per client a month, described as who, what, how (channel), when and where. Thousands of hand-built features were cut back to about 100 raw ones, and the transformer learns the relationships (5:43–7:16)
  • Tokenization is the secret sauce: Amounts, time between transactions, IP addresses and categoricals of very different sizes each need a value-to-token scheme. Zip codes are grouped by distribution (about 2,800 tokens) instead of one token each, so the vocabulary stays trainable (7:59–10:01)
Model and training
  • ~1B now, 11B next: It is a decoder-only model sized with Chinchilla maths. 1B was the smallest size with the biggest gain, and an 11B version is in progress. They started at 20 tokens per parameter but needed about 10× more (10:01–11:56)
  • Off-the-shelf recipe: Causal/masked language-model objectives, mixed precision, distributed data parallel, RoPE, flash attention and activation checkpointing. He says nothing here is new (11:56–13:20)
Fraud results
  • Attention over history: XGBoost loses how a transaction relates to the customer's past transactions, and attention keeps it. Decisions must come within 250 ms, and he says they were well inside that. Detection went up and false positives went down versus production XGBoost, which he says saves millions of dollars, but he gives no exact metrics (13:46–16:30)

How to Let AI Agents Sign Up for Your App Safely — Isabelle Williams, WorkOS

AI Engineer · Isabelle Williams, product manager, WorkOS · uploaded 23 Oct, 1:30 PM IST · 18:33
Verdict: skim from 3:45. The auth.md + ID-JAG signup story repeats Michael Grinich's WorkOS talk from 12 Oct; the anonymous claim flow, the ID-JAG breakdown and the scoped agent-token demo (from 11:49) are new.
🔁 Repeat: 'agent governance' — seen 7 times before. New here: a working pattern where an in-app agent gets its own token whose scopes are the overlap of the user's permissions and the agent's preset limit, so it can be audited and revoked separately.
Letting agents in
  • Three questions: Using Waypoint, a travel app she vibe-coded with Cursor, she asks how to let agents in, how to tie them to real customers, and how to limit and revoke them, since corporate travel involves compliance and money (0:39–2:11)
  • auth.md front door: A markdown file hosted by the app that tells agents how to get access, create an account and call the API. The app still enforces auth (repeat) (2:14–3:11)
  • Anonymous mode, then claim: The agent gets an access token plus a claim token. Later the user follows a link, signs in and enters a one-time code to move the agent's work into their account, and OAuth issues a user-bound token. She notes that this signup step is where product-led growth loses users (3:45–5:10)
Skipping signup with ID-JAG
  • Provider vouches for you: After the user consents to share name and email, the agent asks its provider (e.g. Claude) for an ID-JAG and sends it to the app's authorization server. The app decides whether to create or link an account and which scopes to grant (repeat) (5:10–7:11)
  • Inside an ID-JAG: It is an IETF spec, the same one behind Anthropic's enterprise-managed authorization in MCP and Okta's cross-app access. It is a signed assertion with type, algorithm and key ID in the header, and issuer, the user's name, email and verified flag, audience/client ID and expiry in the payload, signed with the provider's key (7:11–9:09)
  • Demo: As a brand-new user, Sam Rivera, her agent harness skips Maple (needs a browser signup) and TripIt (needs an API key) and picks Waypoint. It asks consent, including an elevated dinner-booking permission, creates the account, books dinner at Quality Bistro and returns a shareable itinerary with no human steps (9:14–11:29)
Limiting and revoking agents
  • Agent tokens, not user tokens: In-app agents get their own token so actions are traceable to the agent, it can be revoked without ending the user's session, and its scopes can be limited. Scopes are the overlap of the user's permissions and the agent blueprint's ceiling, and the token's subject is the agent ID acting on behalf of the user (12:09–14:38)
  • Funding-agent demo: Asked to fix Alex's $250 shortfall, the agent moves the $70 left but can't change the budget. Jordan raises it to 2,000 with his own token, and the agent then finishes the job (14:46–17:43)

Don't Trust Your AI Agents. Test Them Like a Scientist — Stephanie Jarmak, Omni Analytics

AI Engineer · Stephanie Jarmak, AI engineer, Omni Analytics (ex-Sourcegraph, ex-astronomer) · uploaded 23 Oct, 12:30 PM IST · 17:12
Verdict: skim from 2:50 — mostly familiar eval advice; the harness swap, the 295-vs-6 files example, the 10,000-review math and the tamper example are the new parts.
🔁 Repeat: 'evals for agents' — seen 36 times before (WolfBench, Amazon AGI Lab's 80% reliability, Air Canada's no-benchmark evals and others). New here: a harness-only swap moving results 30%+, a recall-vs-precision example and an agent trace that missed tampering.
🔁 Repeat: 'harness engineering' — seen 24 times before. New here: only the harness-swap result; the "evaluate your own config" lesson is familiar.
🔁 Repeat: 'human-in-the-loop review' — seen 16 times before. New here: the 1% false-alarm → 10,000 reviews math.
Why benchmark numbers mislead
  • Cheaper, but still wrong: At Sourcegraph, a prompt change to get Amp to use the code-search MCP tool made runs 28% cheaper, but the agent still never called the tool, so the cost gain didn't answer the real question ((1:11–2:47))
  • The harness swings results 30%+: A third party ran ~63 tasks from a popular coding-agent benchmark (captioned "Turbo Bench 4"); Opus 5 beat Astra in OpenHands, but swapping only the harness put Astra well ahead ((2:50–4:00))
  • Benchmarks are for shortlisting: Public benchmarks give a landscape and a shortlist, not a decision; a law firm shouldn't pick models off Terminal-Bench. Build internal benchmarks that reflect real workloads and hill-climb on them (repeat) ((4:02–5:30))
Running evals like an experiment
  • Design the experiment: Cover task families (she built CodeScaleBench because SWE-bench was mostly bug fixing, and a model can be better at code understanding than bug fixing), do repeated runs because results vary, and watch for model × harness interaction effects (repeat) ((5:33–7:00))
  • Trace the pipeline: Keep all traces and check step by step: was the tool available, was it called, what came back. Even when the agent finally uses the better tool, the final outcome may not change ((7:05–8:38))
  • Pick the right metric: She optimized search for an F1-style balance; with grep, Claude pulled 295 files when only 6 were needed. Recall of 1 looks perfect if recall is all you measure ((8:41–9:51))
Gates, reviewers and records
  • Flagging isn't stopping: In her own software factory, an agent noticed things going wrong but had no way to enforce a stop. Put the gate in code, separately from the agent that flags the problem ((9:55–11:11))
  • Review capacity: An LLM-as-a-judge audit had a 1% false-alarm rate. Sending every alarm to a human would have meant 10,000 reviews, more than domain experts can handle ((11:13–12:05))
  • The agent's record can lie: Researchers planted security issues, and a hash-based tamper check passed everything. An independent comparison of all traffic and model changes caught every one ((12:09–13:17))
  • Production is truth: Omni classifies real usage (easy-to-hard Q&A, dashboard and app building) into eval sets, then measures after deploy or in shadow mode. Agents propose next action, reason, scope and which human check could be dropped, so humans set the autonomy bounds. Her skills repo and a 300-page archive are linked for agents to read ((13:21–17:00))

This Open-Source Tool Generates UI Like Magic

Better Stack · Warren · uploaded 23 Oct, 11:30 AM IST · 6:45
Verdict: skim from 1:21 — a quick, new explainer of generative-UI specs; the token comparison with JSON Render and A2UI is the useful part.
The demo
  • An app launcher with no source code: Type a name like "calculator" or "coffee shop finder" and Gemini 3.8 Flash generates the app and its icon on demand, streamed in and working (20 + 5 works, the coffee finder loads Google Maps). Rendering uses OpenUI ((0:00–1:26))
  • What it's for: Small on-demand UI for data or forms in chat. He links it to ChatGPT's new "intelligent UI". OpenUI's own demos turn "plan a day in San Francisco" into a map, pills and an activity list, and build a playable drum pad ((1:32–2:44))
How OpenUI works
  • A spec, not a library: It works with React, Vue or Svelte and shadcn/Tailwind, Chakra or Material. OpenUI's own component library is optional ((2:44–3:06))
  • Why not JSON: Nested JSON can't be parsed until the whole response arrives. OpenUI Lang is a compact line-by-line format that renders as it streams and uses fewer tokens ((3:06–3:43))
  • Wiring: `@openuidev/react-ui` supplies a system prompt describing your component list and OpenUI Lang, and `@openuidev/react-lang` turns the model's output into React components. Everything runs on your own server and client ((3:43–4:13))
  • Vs. the alternatives: Vercel's JSON Render also streams line by line but uses 2×+ the tokens and 2×+ the latency. Google's A2UI (also supports Flutter) uses 2×+ the tokens ((4:13–4:58))
Limits
  • Where it fits: Generative UI in chat, charts for viewing data, and richer input than the same radio-button card every time ((5:00–5:19))
  • What broke: The demo isn't production-ready. Cerebras ran Qwen 3.8 at 1,800+ tokens/s, but it built broken apps and kept hitting rate limits, so he switched to Gemini. His vision: a secure backend in a user-scoped sandbox, with only the frontend generated ((5:28–6:26))
