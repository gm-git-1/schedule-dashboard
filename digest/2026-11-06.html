AI Agents Will Upend Investing Even More Than Coding - Frank Long, Coatue

AI Engineer · Frank Long, Coatue · uploaded 6 Nov, 5:30 AM IST · 14:04
Verdict: worth watching — a clear systems framing for agentic investing, not a product pitch.
🔁 Repeat: 'AI agents' — seen 108 times before, 'coding agents in production' 60 times, 'harness engineering' 30 times, 'AI for finance' 25 times and 'decision models' 8 times. New here: Coatue's 'hedge fund as a function' framing (external+internal context → selection/size/timing), a Korean-news gather pipeline as a hyperparameter search over runners (code / classical ML / LLM / human), and the claim that maximizing quality—not automating everything—is the goal.
Hedge fund as a function
  • Bigger than coding: Long's Coatue bet is that agents will hit investing even harder than coding; he models a hedge fund as a function of external + internal context that emits a (selection, size, timing) tuple and a time series of those tuples as the portfolio (0:00–0:52)
  • Same pixels, via API: Anything a human sees on screen should be available to an agent by API—news, prices, filings externally, plus positions, liquidity/risk limits and past case notes internally—otherwise it's like hiring great investors and locking them out of 75% of systems (1:31–3:28)
  • Culture as data: He credits KKR-style data culture and Coatue filing every note on trades made or skipped for decades, which is what makes the firm AI-ready (2:23–3:28)
Decompose, then tune
  • Gather → analyze → decide: Jam-everything-into-context won't yield the three numbers; each stage's output is the next stage's input, with nuance in gather (e.g. Korean NBA noise vs local permitting that hits data centers) (3:28–4:59)
  • Korean news case study: For Asia/Korean media on semis/AI—where staff don't speak Korean—collection alone has knobs (MCP vs CLI, chunking, images-as-images vs OCR-to-text) he treats like ML hyperparameters, then filter, translate/extract/summarize, and cross-check against internal notes (4:59–7:24)
  • Four runners: Prefer deterministic code (e.g. P/E < 15), classical stats/ML for richer patterns, LLMs for summarization, and humans for meetings with management; "no glory in automating for its own sake"—pick the runner that maximizes quality (7:24–9:26)
  • Infinite search space: Control-flow forks plus model/harness/skills/hooks make the space combinatorial; without a North Star metric to hill-climb, teams just fidget—and one news-filter subgraph is a tiny slice of the real Kensho-scale graph (9:26–13:16)

Stop Giving Your AI Agents API Keys - Kim Maida, Keycard & Mason Egger, Temporal

AI Engineer · Kim Maida (Keycard) & Mason Egger (Temporal), workshop · uploaded 6 Nov, 2:30 AM IST · 52:36
Verdict: skim from 10:28 — the workshop demo and Temporal kill/recover are useful; the opening OAuth explanation is familiar if you've seen agent-auth talks.
🔁 Repeat: 'coding agents in production' — seen 60 times before, 'MCP servers' 38 times, 'agent security' 31 times, 'human-in-the-loop review' 31 times, 'secrets management' 12 times, 'agent identity' 10 times and 'agent auth' 5 times. New here: a live Expense Desk workshop: OAuth 2 token exchange (RFC since 2020) minting per-tool-call tokens through agent→MCP→ledger hops with Keycard audit of the delegation chain; agent auto-approves under $50 while humans approve over that; Temporal durable settlement that survives killing the worker mid-run without redoing LLM calls, with Keycard interceptors keeping JWTs out of event history.
Why API keys fail (repeat)
  • No attribution, full blast radius: Shared API keys aren't tied to a user or agent identity, grant everything on the key, and human-in-the-loop everywhere still fails for autonomous agents (1:17–1:59) (repeat)
Token exchange path
  • Narrow then exchange: After the user logs in and consents to scoped delegation, the agent app (Expense Desk LangChain agent → expense MCP → ledger API) mints a short-lived token per proposed tool call via Keycard's STS, carrying agent identity + user subject token + requested scopes; policy gates issuance (1:59–7:00)
  • Two hops, discard immediately: Agent exchanges for an MCP-scoped token, MCP validates and exchanges again for a ledger-API token scoped to that call; neither stores the token (7:00–8:49)
Expense Desk demo
  • Before: anonymous API keys: Filing a $75 snack expense and approving someone else's shows only "access granted by API key"—no who created or who approved (10:28–12:51)
  • Agent identity alone: With client ID/secret (workload identity preferred in prod; Keycard vault holds the LLM key), "continue as agent" shows approval limit ~$50 and a $75 swag expense attributed to the agent app, visible in Keycard's audit as a client-credentials grant (12:51–31:22)
  • Human + agent without impersonation: After GitHub login, approval limit is $100; a $30 office-supplies expense is created by the user then auto-approved by the agent under $49.99; a $75 expense stays pending, and the agent refuses to approve the user's own expense—activity shows who filed vs who approved/rejected (31:22–38:09)
  • Traceable delegation chain: Keycard session IDs link hop 1 (agent app on behalf of user → expense MCP) to hop 2 (MCP on behalf of user → ledger API) (38:09–41:26)
Temporal durability
  • Workflow = agent loop, activities = tool calls: Keycard's `@grant_resource` interceptor mints identity at activity time; Egger starts a settlement worker (PID 572), kills it mid-run after debiting 4,200, then restarts—Temporal replays event history, no LLM re-calls, user may not notice a ~5s gap (41:26–49:28)
  • Secrets stay out of history: A check finds no JWT material in the workflow event history (interceptor JIT credentials); optional payload encoder/sidecar can encrypt all Temporal payloads (49:28–52:00)

How Netflix Evaluates AI When There's No Right Answer - Cameron Wolfe, Netflix

AI Engineer · Cameron Wolfe, Netflix (staff research scientist) · uploaded 6 Nov, 1:30 AM IST · 17:52
Verdict: skim from 4:27 — solid overview if you're building subjective evals; skip if you've already internalized judge calibration and A/B loops.
🔁 Repeat: 'evals for agents' — seen 57 times before, 'agent observability' 32 times, 'human-in-the-loop review' 31 times and 'LLM-as-a-judge' 13 times. New here: a three-part framework (human eval as North Star → offline LLM judges/rubrics with meta-eval → production A/B) aimed at highly subjective tasks; power analysis for eval size; a Netflix project where an LLM judge was causally correlated with streaming abandonment; Dr. Tulu-style task-specific rubrics vs high-level judges.
Why subjective evals drown in noise
  • Small suites, non-deterministic agents: Benchmarks can cost $50–100k to run, so task sets stay small; agent + grader noise makes results hard to trust, and most public work still targets verifiable tasks (string match, symbolic checks) (0:50–2:43) (repeat)
  • Spectrum of verifiability: Math sits at the deterministic end; creative writing sits at the subjective end, where replacing a deterministic grader with another LLM adds noise (2:43–3:54)
Three-part framework
  • Human eval as North Star: Partner with a few SMEs on quality guidelines (binary/Likert criteria + examples), then calibrate by multi-rater agreement and revising guidelines until humans agree (4:27–6:05)
  • Power analysis for sample size: Estimate volume from effect size, observed noise (e.g. resampling completions), and significance; sample for diversity, production realism, and discriminative difficulty via profiling (6:05–8:10)
  • Offline judges and rubrics: High-level LLM judges mirror human guidelines; rubrics (e.g. Dr. Tulu culturally adapting a book into a Netflix film) are task-specific checklists verified item-by-item for more objectivity (8:10–9:47)
  • Meta-evaluate the judge: Compare judges to golden human labels (correlation, accuracy); at Netflix, one LLM judge's outputs were causally correlated with abandonment—use human–human agreement as the target agreement level (9:47–11:45)
  • Fight noise with stats: Power analysis, error bars, and resampling of both model and judge rollouts so a higher score means a real capability gain (11:45–13:17)
  • Production A/B as soft deploy: Explicit (thumbs) and implicit (session length, abandonment) metrics; A/B before full rollout, then feed new failures back into offline/human evals (13:17–15:45)

Why Waiting for the Next AI Model Can Pay Off - John Stecher, Blackstone & Scott Worland, Norm AI

AI Engineer · John Stecher (Blackstone CTO) & Scott Worland (Norm AI CTO), fireside · uploaded 5 Nov, 3:30 PM IST · 20:45
Verdict: skim from 8:54 — the wait-for-model ROI rule and Norm's rewrite story are the keepers; data-strategy and evals advice is familiar.
🔁 Repeat: 'coding agents in production' — seen 60 times before, 'evals for agents' 57 times, 'harness engineering' 30 times, 'AI for finance' 25 times and 'AI in regulated industries' 25 times. New here: Blackstone CTO John Stecher's explicit ROI rule for waiting on the next model when today's build isn't pressing; Norm AI's early-2024 map-reduce scaffolding becoming obsolete once agents worked, a Sprinter-van Airbnb rewrite of the platform, tens of thousands of expert-labeled evals, and Stecher's comfort throwing away internal apps and rewriting when cheaper than versioning forward.
Get the foundations right
  • Data strategy first (repeat): Stecher's top failure mode for portfolio companies is jumping to agents without moving data out of transactional systems into something agents can access; Blackstone weaves proprietary + public data for that (1:32–2:21) (repeat)
  • Straight-through processing still matters: He uses agents (e.g. Factory) to map human workflows, then writes code for STP and only injects agent intelligence where humans used to decide rote work; also points agents at SDLC chores like tests and library renovations (2:21–3:46)
Norm's bitter-lesson arc
  • Scaffolding → obsolete: Founded 2023, Norm built highly structured map-reduce-style workflows for regulatory consistency and amassed tens of thousands of expert-labeled eval samples; when tool-using agents arrived, much of that hand-written scaffolding looked obsolete (3:46–6:42)
  • Sprinter-van rewrite: Engineering leadership rented a Sprinter, drove to an Upstate NY Airbnb after a snowstorm, and respec'd a platform for agentic client experiences plus AI co-developers (5:05–6:42)
  • Evals are the duty in finance (repeat): Stecher stresses high quality bars—model or harness or data changes skew answers—so continuous evals measure system health (6:42–7:40) (repeat)
When to wait vs ship
  • ROI vs next-model: Stecher regularly delays builds when six months of better models/cheaper compute will solve it and there's no pressing business value today (8:54–10:25)
  • POC fast, production hard: Lean into harnesses to get clickable POCs without PowerPoints; don't count tokens—but getting into finance infra, cybersecurity, and SRE-traceable production still takes human-owned core primitives (10:25–17:24)
  • Throw away internal apps: Ten years ago rewriting was insane; now he asks whether rewriting costs less than versioning forward, and Norm keeps "conduits" for frontier models instead of dams (17:24–19:13)

How We Took an AI Agent From 41% to 97% Accurate - Milind Sunil Shah, Brainbase Labs

AI Engineer · Milind Sunil Shah, Brainbase Labs (MTS) · uploaded 5 Nov, 2:30 PM IST · 13:22
Verdict: worth watching — rare before/after numbers and two browser-use failure modes with one-line fixes.
🔁 Repeat: 'AI agents' — seen 108 times before, 'coding agents in production' 60 times, 'evals for agents' 57 times, 'LLM-as-a-judge' 13 times, 'browser agents' 8 times and 'computer-use agents' 4 times. New here: Domino's competitor pizza-pricing agent: V1 41% accuracy / $2 per source / 129 min → V11 97% / $1 / 71 min via instructions/skills only; ontology with Postgres-like memory; offline evals from analyst sheets + archive.org + screenshots; 'agent as a judge'; fixes for missing below-the-fold deals and image-zoom loops (DOM-first cut image reads ~1/3 and cost >50%).
The Domino's problem
  • Competitor pricing spreadsheet: Across 20k+ stores / 90+ markets, CMO analysts spent ~2 hours/day checking competitor delivery-app and website prices with promos; one wrong step yields a finished-looking wrong cell (0:26–1:36)
  • 41% → 97%: V1 was 41% accurate at $2/source and 129 minutes; V11 hit 97% at $1/source and 71 minutes, changing only instructions, skills and playbooks (1:36–2:02)
Six-step framework
  • Kickoff: Agree on win—job, human sign-off, time/cost/accuracy, who judges, what the agent must never assume alone (2:23–3:35)
  • Ontology (not anthology): Define every term so the agent never guesses—e.g. pay-at-checkout price not strikethrough, large pizza = item or bundle, delivery ≠ takeaway, compute 30% off before writing, gap not guess; Brainbase memory as a Postgres-like store with target + price_observations tables (3:35–5:43)
  • Benchmarks and three judges: Offline from past analyst sheets; archive.org snapshots failed for delivery apps so they stored browser screenshots from V1; code checks (ID filled, discount math, ±20% vs prior flagged), LLM-as-judge on item/promo choice, agent-as-judge that re-checks flagged prices with tools (5:43–7:42)
  • Narrow V1 then widen: One app, one item, one city → burgers/takeaway → another app → more sites; V1's job is to be measured, not good (7:42–8:49)
Two concrete fixes
  • Deal below the fold: Agent stopped at the linked pizza section and missed a $21 deal lower on the page; rule: scan the whole page, not just the deep link (9:44–10:28)
  • Zoom loop on promo images: 26 image promos, found the card at minute 13 then zoomed 4–6x until manually stopped at 15; rule: read HTML DOM / alt text first, cap zoom—cut image reads to ~1/3 and cost over 50% (10:28–11:56)
  • Hand off the loop: Agent runs on schedule/email trigger; analysts review exceptions; corrections become benchmark cases; expanding to more markets (11:56–13:22)

Stop Making Your Customers Click Approve - Emil Chetty, Wise

New here: Wise's 'agree to the job, not every step' model: trusted software turns a vague prompt into an immutable human-readable + machine-readable authorized job; intersection of confirmed job ∩ Wise policy ∩ Sarah's rights provisions payment/reconciliation workers; prompt injection updating payee fails at service check because belief can't rewrite the confirmed job; Wise scale ($243B cross-border, ~19M customers, 80+ licenses).
The promise vs the queue of requests
  • Wise scale: Account, Business, and Platform on one network of 90+ local banks/providers; last year >$243B cross-border volume, nearly 19M active customers, 80+ licenses—regulators still need to know what was authorized and explain outcomes (0:58–3:36)
  • Eight approve clicks: A typical "handle this week's approved supplier payments" job becomes a familiar approve-each-step UX—the coding-agent "before times" without skip-permissions, making the human the API (3:36–5:35) (repeat)
Safe action ≠ authorized payment
  • Different question: Coding agents ask "does this look safe?" (auto mode, classifiers, sandboxes); payments ask "did this customer authorize this payment to this recipient on these terms?"—evals/harnesses alone don't prove agreement (5:35–6:42)
  • Intent → locked agreement: Trusted software (built since 2011) gathers read-only context, resolves suppliers/amounts, shows Sarah a draft (e.g. three suppliers, ~$775 + fees) plus what the agent may decide vs escalate; approve+authenticate makes that exact version an immutable authorized job (6:42–10:27)
  • Provision from the intersection: Deterministic check of confirmed job ∩ what Wise permits ∩ Sarah's current rights grants limited rights to payment and reconciliation workers; plan may change inside the agreement, new terms need a new proposal (10:27–12:35)
  • Retries vs quote changes: Shared payment state means a restarted pod follows the existing job (not a duplicate); expired/changed quotes return to Sarah—the agent prepares an update but can't approve it (11:32–12:35)
  • Prompt injection fails closed: Even if the agent believes new payee details, the service check rejects against the confirmed job; the boundary is software enforcement, not the model spotting the scam (13:25–14:18)

TypeScript Got Ported To Rust... And It's 3x Faster Than Go

Better Stack · Warren · uploaded 5 Nov, 12:30 PM IST · 5:19
Verdict: worth watching — short, with side-by-side numbers and a clear AI-porting story.
🔁 Repeat: 'open source / local models' — seen 52 times before, 'AI-generated code validation' 32 times, 'JS/TS ecosystem' 12 times and 'dev tools' 11 times. New here: Warren benches tsrs vs Microsoft's Go port vs JS on the TypeScript repo (793 files, ~380k LOC): Rust ~0.3–0.5s vs Go ~0.6–2.2s vs JS ~6.6–13s across four scenarios (~24x vs JS, ~3x vs Go); built in ~3 weeks by directing Claude Opus 5.5 agents to port Go→Rust function-by-function against 13k+ tests (same 26,054 errors on a broken core type); Cloudflare+Vite/OXC want WASM without Go's GC.
What these compilers speed up
  • Typecheck, not emit: ESBuild/Vite strip types fast; type checking on big repos still takes minutes—that’s what the Go and Rust ports target (0:40–1:32)
Benchmarks on the TypeScript repo
  • Setup: 793 files, ~380k LOC; four scenarios (all valid, one error, broken core type, recursive type too deep) (1:32–2:00)
  • Numbers: Valid: JS ~7s / Go ~0.7s / Rust ~0.3s; one error: 6.6 / 0.6 / 0.2; broken core type: 13 / 2.2 / ~0.5; recursive: ~7 / 0.8 / 0.4—Go ~9–10× JS, Rust ~24× JS and ~3× Go (2:00–2:53)
How it was built
  • Three weeks with agents: Microsoft’s Go port took ~2 years (announced Mar 2025); the Rust port’s first commit to announcement was ~3 weeks—one engineer directed Claude Opus 5.5 agents to copy the Go compiler function-by-function against TypeScript’s 13,000+ programs; Rust passes all tests and matched Go’s 26,054 errors on the broken-core-type case (2:53–4:06)
  • Why Rust / Cloudflare: Developed with Cloudflare and the Vite team inside OXC for WASM in sandboxes/browsers—no GC to ship; TypeScript team suspects some Rust speed tricks are already feeding Microsoft’s next Go release; planned for type-aware lint in Oxlint (4:06–5:19)
