Orbit as workflows, not autopilot
  • YAML is the agent: Every Orbit agent is one YAML file in a repo, reviewed via the same merge-request process as other code; a code-review step fetches MR metadata, classifies risk, clones read-only, then calls the model with a strict output schema and no write permission (4:13–5:46)

Runtime controls
  • Split orchestration from runtime: Started as one ECS Fargate container; now separates orchestration, agent runtime, and session state, with timeouts, aggressive rate limits, and locks that drop duplicate runs (e.g. a second code-review request) (8:29–11:04)
  • Per-step allowlists (repeat): Each LLM step reuses the Claude Agents SDK but restricts network, tools, skills, and MCP servers down to named tools — declared in YAML so a review step can search code but never edit or push (11:04–13:10)
  • Skills → workflows: A central skills marketplace feeds both laptop Claude Code and Orbit; teams start with a cheap skill, then graduate a proven task into a background workflow (12:07–13:10)
Evals and scale

  • 30-day numbers: Code-review agent >9,700 runs (<3 min/MR); plus audit fixer 159 MRs, AI-readiness ~80 repos, Victoria linter 413 projects, merge-conflict resolver 921 — >11,000 executions at 99% execution success (not answer correctness) (15:44–16:21)

No transcript available yet; this entry is built from the video's chapters and description only.

Why fixed flows and free agents both fail
  • Multiday "fill out a form": A wealth request like "fill out a form for Mr. Harper" expands into identify household → find missing info → contact client → wait → follow up → signature → retain evidence — days of ambiguity a flowchart can't absorb and an improvising agent can't be trusted with (2:19–6:45)
  • Draw the deterministic boundary: Control flow, evidence, and external actions stay in a deterministic system; models only do interpretation and judgment at explicit typed points (6:45–8:01)
Typed plans that can be refused
  • Planner → semantic graph → compiler: The planner maps a request to a semantic graph whose nodes point back to the request; a compiler validates against the firm's action contracts and returns a valid plan, a clarification, or a refusal (8:01–9:56)
  • Immutable approvals and payload gates: Approved plans are immutable; external actions get separate gates tied to the exact payload. Waiting/follow-ups are state-machine steps; uncertain side effects go to manual review, not automatic retries (9:56–12:52)
Model mix and private inference
  • 19/20 to a smaller model (design target): An illustrative 20-decision run assigns 19 decisions to a smaller model and one to a frontier model — stated as a design target, not a measured fleet result — aiming toward privately hosted inference and future training on typed, logged judgments (12:52–15:21)

Just-in-Time Ontologies: What Cheap Intelligence Means for Data — Hrishi Olickel, Southbridge AI

AI Engineer · Hrishi Olickel, Southbridge AI · uploaded 12 Oct, 9:30 PM IST · 21:03
Verdict: worth watching — rare concrete data-pipeline failure modes and cost numbers; the ontology framing actually earns its length.

Why universal schemas fail
  • $10k → under $800 in 10 days: An Ohio campaign-finance entity-resolution pipeline projected at ~$10,000 was reworked after "Jeff" launched; 10 days later every donor case had ground truth for under $800 (1:14–1:44)
  • Four schemas, not one: Source, storage, decision, and model-prior schemas only align when the question is known — "customer" means payer to billing, caller to support, liable party to compliance — so ontologies should be built just-in-time for the decision (1:44–5:34)
Three model roles in data work
  • Designers vs workers vs hill-climbers: Pipeline design wants slow, thick-token models; in-pipeline workers want cheap/fast/repeatable models (e.g. decision models like Jeff); a third "surfer" class self-optimizes over a stable surface (8:30–10:39)
  • Ohio statewide results: Over a dozen architecture rounds labeled all 23,317 cases; total spend $795 on an $800 budget (checking ~4× doing: $545 vs $128); agent ran ~10 days, >4,000 Hank runs, ~90,000 Jeff calls, ~6B tokens (10:39–13:58)
Priors and silent data bugs
  • Sign-flip disaster: A pipeline treated negative loan amounts as redundant signs and stored absolutes — net $784,000 became $5.3M of debt, validated by multiple models (13:58–15:41)
  • Cross-model prior intersection: On 200 held-out families, Jeff and Luna agreed on 194 with zero shared errors; every error sat in the 6 disagreements — different model families shrink the review surface (15:51–16:42)
Self-optimization requirements
  • Four missing pieces (repeat): Stable deployment surface (Hank), bounded experiment budgets, reusable methodology/patterns, and an explicit failure surface; pilots become reusable "codon" segments that can be reverted and sequenced (16:42–21:03)

Your GPU Neighbor Can Hear Your Model — Branislav Brzak, Stealthium

Verdict: worth watching — unusual hardware side-channel angle on multi-tenant GPUs; captions would help for the math walkthrough.
🔁 Repeat: 'agent security' — seen 11 times before. New here: an H100 timing side channel that never reads victim memory yet infers model depth and workload class.
🔁 Repeat: 'inference / serving' — seen 24 times before. New here: shared-GPU tenant placement / NVLink leakage implications for multi-tenant inference.

No transcript available yet; this entry is built from the video's chapters and description only.

What shared GPU timing leaks
  • Three microseconds matter: Extra latency on the attacker's own memory reads can reveal activity on another tenant's GPU slice — no victim-memory read and no software bug required (0:00–1:54)
  • What it cannot recover: The attack observes timing, not prompt or answer contents; Brzak explicitly separates workload/model inference from recovering actual text (1:54–3:16)
How the probe works
  • Own-memory probe → rates and layers: Repeated reads → frequency analysis → token rates and layer signatures; tempo alone is weak when decoding speeds match, so layer signals help tell similar architectures apart (3:16–7:45)
  • Workload class via speculative decoding: Distinguishing code / prose / JSON / retrieval in the demo depends on speculative-decoding acceptance patterns that change step timing (7:45–9:15)
  • Across NVLink: Moving to a separate GPU on an NVSwitch-connected H100 server still yields a weaker but informative signal over NVLink (9:15–11:23)
Operator takeaways
  • Placement and isolation tradeoffs: Results are for the tested configs, not every shared deployment; operators should weigh tenant placement, isolation vs communication, and watch for probing workloads on the GPU itself (11:23–13:20)

Your Agent Is a Lethal Trifecta (And What to Do About It) — Kim Maida, Keycard

🔁 Repeat: 'MCP servers' — seen 22 times before. New here: MCP as the broker that exchanges per-tool-call tokens for downstream resources instead of holding standing API keys.
The overprivileged on-call demo
  • Standing keys, real damage: With static API keys and an admin DB string, the triage agent dumps customer PII into a ticket, drop-restores a billing database, restarts production, and scales 4→40 pods at $420/hour (0:00–4:16)
  • Lethal trifecta (Simon Willison): Private data + untrusted content (tickets) + external communication (APIs/SaaS) — useful and dangerous together; human-approval alone just shifts consent fatigue up the chain (4:16–8:43)
Why OAuth / gateway / sandbox aren't enough
  • Standing access remains: OAuth grants before any task exist; MCP gateways still hold standing credentials; sandboxes bound the process but not what is authorized outside — none issue a credential downscoped to one task (6:21–8:43)
Token exchange + intent-based auth
  • Subject token through the chain: User logs in → scopes delegated to the agent → subject token identifies who the agent acts for; runtime authenticates to an STS and requests a token for that tool call only (8:43–14:11)
  • IBA as a proposal: Keycard's intent-based authorization is presented as a proposal (not a finalized standard): a mission (goal, allowed actions, limits) is approved, then each tool call is checked against that mission ID before an ephemeral minutes-lived token is minted and never stored (14:11–17:37)
Same demo, task-based policy
  • Deny PII and DB drop; allow cert renew: Customer-warehouse query denied; TLS cert renewal allowed; DB delete refused by STS (20:01–22:28)
  • Approval still bound by user role: Server restart stays blocked even after the user clicks approve because their role can't authorize it; scaling proceeds only when the user has that authority — task-scoped ephemeral access retained (22:28–25:08)

We Let Our Financial Planners Write the Agents — Matthew Ragone, Range

AI Engineer · Matthew Ragone, Range · uploaded 12 Oct, 5:30 PM IST · 8:54
Verdict: worth watching — 9 minutes, a concrete and copyable playbook for getting non-engineers to build skills, from the user's side rather than a vendor's.
🔁 Repeat: 'AI fluency / enablement' — seen 7 times before. New here: a non-engineer (a certified financial planner) gives a 5-step method for building skills, with real adoption numbers from a regulated wealth firm.
Why planners build their own agents
  • The limit is being in one place at a time: Ragone is a certified financial planner, not an engineer, and leads AI adoption at Range, an all-in-one wealth management firm. Typing faster never helped; the gain came when an agent drafts one client's full cash-flow or insurance analysis while he's on a call with another client (0:27–1:04, 1:35–2:28)
  • Agent drafts, planner sends: The agent never sends anything. A planner reviews every recommendation before a client sees it. To get there, the agent had to work where the work lives (not a copy-paste chat window) and know "how Range does it", not generic planning. That firm-specific know-how is what a skill is (2:19–3:14)
Five steps: pick, teach, pack, test, ship (no code)
  • Pick: Choose a workflow you repeat weekly and can judge at a glance, not the flashiest one: low complexity but heavy manual work. For Range that was cash-flow analysis and insurance reviews (3:40–4:25)
  • Teach: Walk through several real past client cases and say your reasoning out loud: why you open a document, what you're looking for, when you'd stop and ask. "That narration is the whole game" (4:28–5:01)
  • Pack: A skill is more than steps. It needs the questions it must ask before starting and the limits it must respect (e.g. never send to a client). Steps alone give you something that "just runs on its own" (5:03–5:49)
  • Test, then ship with an owner and a reviewer: Run it 5–10 times on real cases to catch edge cases, missing questions and confident mistakes before handing it to 15–100 people. Then give it an owner who keeps it current (a skill that's right in March can be wrong by December) and a reviewer who isn't the author (5:51–7:01)
Results after six months
  • 24 skills, 17 in planning: Use spread to sales, product and marketing with no mandate. Every skill is written and maintained by planners, marketers or salespeople, not engineers. Specialists build their own niche (the insurance expert builds the insurance skill), and skills get peer-reviewed the same way plans are (7:04–8:06)
  • The bottleneck has moved: Whether a model can draft a cash-flow analysis is settled. The open questions are who writes down how the firm does it, who tests it, and who owns it once 15 people depend on it (8:08–8:38)
