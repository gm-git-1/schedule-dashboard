Catch the Bugs Your Code Review Misses - Killian Carlsen-Phelan & Taylor Luttrell-Williams, Sonar

AI Engineer · Killian Carlsen-Phelan & Taylor Luttrell-Williams, Sonar · uploaded 30 Oct, 4:30 AM IST · 38:07
Verdict: skim from 15:43 — the three PR demos (15:43–31:30) are concrete, but it's a product workshop and the framing is well-covered ground.
🔁 Repeat: 'AI-generated code validation' — seen 26 times before (Sonar's third talk in two days). New here: a hands-on look at Gitar, Sonar's PR verification agent, rather than SonarQube.
🔁 Repeat: 'human-in-the-loop review' — seen 21 times before. New here: little beyond the "review is the bottleneck" framing.
🔁 Repeat: 'merge queues / CI' — seen 5 times before. New here: an agent that reads failing CI logs, pushes fixes and auto-merges once checks pass.
The pitch
  • Why another reviewer (repeat): Agents ship more code than fixed-size teams can inspect, so review queues grow and production incidents scale with the rate of change, because agents don't know a team's architecture or standards (4:49–6:46)
  • What Gitar claims: It's tuned for a high signal-to-noise ratio (every false positive is a wasted token and a risky fix attempt), separates real CI breakages from flaky or infrastructure noise, fixes issues itself and keeps iterating until CI passes (7:00–8:09) (9:00–10:00)
Three pull requests on a sample ticketing app
  • A bug outside the diff: PR 1 adds "transfer a ticket to a friend" with passing tests. Gitar flagged that the buyer could still cancel and refund the original order, voiding the friend's ticket, and pointed at the existing `orders.py`, not the changed lines. Commenting "gitar fix" pushed a fix and re-verified it (16:06–16:40) (18:31–20:40)
  • Static analysis versus intent: Killian's point is that SonarQube-style analysis traces things like SQL injection across 20 files but can't infer intent from the title, description and existing code, so both layers are needed (16:40–18:00)
  • Business rules from config: PR 2 adds a $3.50 service fee, but the company rule is that every price shown is all-in. Markdown context files in `.gitar/review` and trigger-based rules in `.gitar/rules` made Gitar flag the non-all-in price. A rule can also fetch a Slack thread linked in the PR description and check the code against it (22:35–25:30)
  • CI diagnosis and auto-merge: PR 3 refactors ticket scanning and fails the test "ticket cannot be scanned twice" (a reused ticket returned 200). With a GitHub ruleset requiring status checks plus the comments "gitar auto apply on" and "gitar auto merge on", Gitar kept pushing fixes and merged once CI went green (27:11–31:30)
Extras
  • Advanced features: Functional validation checks each PR against its Jira or Linear ticket, "knowledge" learns conventions and false positives weighted by reviewer seniority, cross-repo analysis catches PRs that merge cleanly but break another repo, and cross-PR analysis checks in-flight PRs against each other (34:07–36:00)

Why Humans Can't Keep Up With AI-Written Code - Tariq Shaukat, Sonar

AI Engineer · Tariq Shaukat, CEO, Sonar · uploaded 30 Oct, 12:30 AM IST · 16:35
Verdict: skim from 6:13 — the five problems with their study figures (6:13–10:25) are the useful part; the rest is a Sonar keynote pitch you've heard this week.
🔁 Repeat: 'AI-generated code validation' — seen 26 times before (Sonar's fourth talk in two days). New here: a set of cited studies on why human and LLM review both fall short.
🔁 Repeat: 'software factory' — seen 12 times before. New here: the Toyota/Lexus factory analogy.
🔁 Repeat: 'human-in-the-loop review' — seen 21 times before. New here: the "cognitive surrender" study.
🔁 Repeat: 'LLM-as-a-judge' — seen 9 times before. New here: PayPal and Meta figures on judges flipping verdicts.
The factory analogy
  • Ball bearing on the seams: Lexus's ad rolling a ball bearing across a car's seams showed the shift to building for quality, fixing the system, and letting anyone stop the line. Agile, Kanban, error budgets and CI came from the same Toyota ideas (0:26–2:55)
  • Code is cheap now (repeat): One study of async agents found lines of code up 2,450% and commits up 240% but releases up only 30%. Sonar's upcoming survey says 5% run agentic software factories today and 34% expect to in a year (39% in financial services), the same preview Sonar gave yesterday (3:22–4:05) (5:36–6:00)
Five hard problems
  • Humans rubber-stamp: In a "cognitive surrender" study people agreed with AI 93% of the time when it was right, and four out of five times when it was wrong (6:13–6:40)
  • Big codebases and compounding errors: Agents translated code correctly 91% of the time at 10,000 lines, but accuracy collapsed by 50,000. Token use for the same task varied 30x. METR rates Claude Mythos at 16-hour tasks only at 50% success, and 95% per-step accuracy falls to about 36% over 20 steps (7:00–9:05)
  • Unreliable judges: A PayPal AI paper found 7–17% of verdicts change across identical runs, and a Meta study found a simple "are you sure?" flips the answer 7–34% of the time. With time-to-exploit near zero, prevention has to be built in (9:06–10:25)
Sonar's answer
  • Code confidence formula: Intent times guide rails times independent verification times evidence, multiplied because any one at zero makes confidence zero (10:29–12:15)
  • Customer claims: Sonar Vortex (intent and guide rails in the agent loop) cut token cost 36% and issues per commit 92%. In a survey of 1,000+ customers, SonarQube users were 81% more likely to report a very positive effect on code security, 34% on time to market and 76% on outage frequency (12:36–15:00)

How Revolut Cut AI Coding Costs 90% With Self-Hosted Open Models - David Abitbol, Revolut

AI Engineer · David Abitbol, head of AI operations, Revolut · uploaded 29 Oct, 2:30 PM IST · 11:47
Verdict: worth watching — short and packed with real numbers on self-hosting cost, latency and tuning.
🔁 Repeat: 'open source / local models' — seen 46 times before. New here: real production numbers from a bank running GLM for 2,000 engineers.
🔁 Repeat: 'inference / serving' — seen 35 times before. New here: the latency targets and tuning settings that got 88% faster on the same GPUs.
🔁 Repeat: 'token costs / AI spend' — seen 12 times before. New here: a blended 30 cents per million tokens, about a tenth of their frontier-lab bill.
🔁 Repeat: 'AI in regulated industries' — seen 16 times before. New here: how an EU-regulated bank argues compliance for Chinese open-weight models.
What AI did to 2,000 engineers
  • The timeline: Gemini (January 2025) gave about 10% better lead time and 20% better coding time. Claude Code, rolled out with strict budget limits because some engineers spent $1,000–$10,000 a month, made little difference (1:24–3:00)
  • Unlimited tokens changed it: Self-hosting GLM from April 2026 brought about 60% better coding time and 70% better lead time. Lead time improved more, so coding isn't the bottleneck; people used the tokens on inbox, Jira and Confluence work. Codex and Claude Code are now the exception (3:00–4:22)
The numbers for self-hosting
  • Hardware and targets: 56 B200 GPUs serve GLM-5.3 (about 800B parameters) to 2,000 engineers. Keep time to first token under 3 seconds (over 5 and his Slack blows up); 200 tokens per second is enough, and after 5 PM engineers get about 800 (4:24–5:32)
  • Cost: Blended cost is 30 cents per million tokens, and the invoice is about a tenth of what they paid Anthropic and OpenAI (5:32–5:46)
  • Tuning: On the same 56 GPUs, requests per second went from about 3 to over 7 and time to first token from over 10 seconds to about 1.6 between April and August, which he calls 88% better performance for 76% more demand (5:59–7:06)
  • Settings that mattered: "Long context is a scam": serve 256K, not 1M. On Blackwell use NVFP4 (about 40% less GPU footprint than FP8 for no precision loss), try TP8 instead of TP4 for more KV cache, keep coding cache hits above 90%, and look at speculative decoding (7:14–8:14)
Production and compliance
  • Setup: GLM is text-only, so a local router sends image tasks to another model, and the OpenAI-compatible endpoints plug into OpenCode and Codex (8:17–9:20)
  • For the CIO: Using the weights on your own servers isn't sending data to China. Coding tasks are human-in-the-loop, enforced by a sandbox with approval rules (allow grep, not Gradle), which keeps regulators from treating it as an autonomous agent. Keep data in data-adequacy countries, insist on zero retention, and run strong OpenTelemetry logging (9:32–11:40)

We Trust AI Agents That Break Every Day - Shy Ruparel, Temporal

AI Engineer · Shy Ruparel, developer advocate, Temporal · uploaded 29 Oct, 1:30 PM IST · 21:32
Verdict: skim — the survey numbers (3:16–10:40) are new data; the demo is Temporal's familiar durable-execution pitch.
🔁 Repeat: 'AI for finance' — seen 15 times before. New here: little; finance is the framing.
🔁 Repeat: 'agent observability' — seen 26 times before. New here: the argument that seeing a failure isn't recovering from it, and that one event history can serve both.
Temporal's State of Development survey (554 engineers)
  • Usage versus production: Daily agent use doubled from 47.3% last year to 80.8%, but only 49.1% run agents in production or call them core to shipping (3:16–4:33)
  • Trust versus reality: 85.5% trust agent output at least somewhat, yet 41.1% hit agent issues daily or more and 16.4% hourly. Teams calling themselves successful were 1.7x more likely to hit issues constantly, and 40% say security blocks autonomous agents (4:46–7:18)
  • Prototype versus enterprise: 51.3% get a prototype production-ready in hours or faster, but at companies with 5,000+ employees about one in five say it takes months, versus about one in 20 elsewhere (7:35–8:55)
  • Seeing versus recovering: The top productivity limits are tracking state (35.7%) and debugging (30.9%), not models. 22.2% lose work to crashes, only 13% are very confident they can debug AI workflows at scale, and the top place people go for help is YouTube (9:05–10:40)
Demo: a $2,500 payout that survives a crash
  • The setup: A nine-step Temporal workflow with a local Qwen 9B model: validate, reserve funds, FX quote, an agent investigates fraud (flagged by an unresolved account alert) and drafts a brief, then a human approves (10:56–12:00) (15:00–15:50)
  • Killing the workers: He stops all workers, approves while none are running (the approval is recorded as a signal), then restarts. In the event history each AI step ran exactly once, so no tool calls were repeated and no tokens re-spent; eight in ten respondents say cost limits their agent use (13:10–15:00) (15:50–18:12)
  • Design point: The workflow owns the money and state while the agent only gives bounded advice; if the model failed, the payout would continue without the brief. State is plain variables rebuilt on replay and retries are a declared policy, not loops (18:12–20:10)
Who uses it
  • In production: OpenAI's Codex and Replit's agents run on Temporal, according to him (20:10–20:40)

Why a One-Line Change Can Break Your Whole Stack - Cole Gannaway, Qodo

AI Engineer · Cole Gannaway, solutions engineer, Qodo · uploaded 29 Oct, 12:30 PM IST · 14:51
Verdict: skim from 2:03 — the blast-radius example (2:03–4:15) and the mid-task review tip are the takeaways; the rest overlaps today's Sonar talks.
🔁 Repeat: 'AI-generated code validation' — seen 26 times before (Qodo's third talk). New here: the cross-repo blast-radius example.
🔁 Repeat: 'human-in-the-loop review' — seen 21 times before. New here: periodic mid-task reviews used to steer the coding agent.
🔁 Repeat: 'context engineering' — seen 17 times before. New here: a software graph of repos and their integration points fed to the reviewer.
Review is the new bottleneck
  • The squeeze (repeat): Customers want ticket-to-production automation and get stuck at PR review, now that code generation moves faster than ever (0:59–2:03)
  • One-line blast radius: A one-line rename in Bitwarden's data model passes the build, unit tests and linters, yet breaks the web, mobile, CLI and MCP clients that depend on the server. Almost everyone in the room admitted merging PRs without reading every line (2:03–4:15)
What Qodo adds
  • Software graph: Qodo builds a graph of a team's repos and their integration points automatically, so a reviewer (human or agent) sees which components a change touches (4:15–4:56)
  • Rules from tribal knowledge: Custom rules (for example, flag any public API change without a deprecation flag) and rules Qodo suggests from past PR comments carry senior reviewers' taste forward, and the same context reaches the coding agent before code is written through MCP or a CLI (4:56–6:29) (8:20–9:20)
  • Writer shouldn't grade itself: A separate review agent keeps more context window free and should differ in model and harness to avoid shared bias. Adversarial reviewers that agree give high signal; if they disagree, look closer (6:29–8:20)
Q&A
  • Catching the wrong intent: Jira or Linear tickets are linked into every review and requirement gaps against acceptance criteria are highlighted. Qodo also recommends a skill that runs a review at the 25%, 50% and 75% marks of generation to steer the agent (10:06–13:55)
