Stop Shipping LLM Settings That Only Win on Paper - Rohan Pandey & Balaji Varadarajan, DigitalOcean

AI Engineer · Rohan Pandey & Balaji Varadarajan, DigitalOcean · uploaded 12 Nov, 5:30 AM IST · 5:33
Verdict: skim — a short, concrete demo of automated vLLM tuning with real numbers, but none of the deeper lessons the description promises.
🔁 Repeat: 'inference / serving' — seen 42 times before. New here: an agent that searches vLLM serving settings automatically with Bayesian optimization instead of hand-tuning.

Note: the video is a 5-minute demo by Rohan only. The four studies, the +4% "winner" that was noise, and the prefill/decode extension promised in the description are not in it.

What the agent does
  • Goal: Find the best vLLM serving configuration for any model automatically, in the background, instead of engineers tuning the recipe by hand (0:00–1:00)
  • Search method: It uses Bayesian optimization, through the Optuna library, to shrink the search space. Each trial runs a recipe, scores it, changes it and reruns until the trial budget is spent (1:00–2:00)
Demo and results
  • Setup: On a DigitalOcean droplet running GPT-OSS 120B, the starting recipe is tested on four traffic patterns (short chat, long chat, RAG and batch classification), each with its own input and output token lengths (2:00–3:00)
  • Running it: You run `tuner.py` with a study name, the starting YAML, the hardware and the number of trials (24 in this example). Runs take a few hours, about four to five for GPT-OSS (3:00–4:00)
  • GPT-OSS result: The HTML report picks the best of 50 trials and outputs an optimized YAML (for example a value of 256 for one setting). Goodput, the tokens served within targets, improved 17.5% over the starting config (4:00–4:55)
  • DeepSeek R1 Distill result: In a 9-trial run the last trial won, token throughput doubled and inter-token latency fell by almost half (4:55–5:26)

Your SKILL.md Is 70% Stuff the Model Already Knows - Nikolay Petrov, Intel

AI Engineer · Nikolay Petrov, Intel · uploaded 12 Nov, 4:30 AM IST · 14:01
Verdict: worth watching — a practical, cheap method for finding the dead weight in a SKILL.md, with real numbers.
🔁 Repeat: 'agent skills' — seen 28 times before. New here: a way to measure, line by line, which parts of a skill the model already knows.
🔁 Repeat: 'evals for agents' — seen 68 times before. New here: little on evals themselves; the with-skill vs without-skill comparison is standard.
Testing a skill properly
  • Two kinds of skills: Some skills teach the model new knowledge, others only steer it through a repeatable process. This talk is about the first kind (0:45–1:30)
  • The usual eval (repeat): Run the same tasks with and without the skill loaded and compare. In his example the model solved 3 of 5 tasks without the skill and all 5 with it, and you also compare tokens and time (1:58–3:00)
Seeing inside the skill
  • Split into checkable items: Borrowing the FActScore idea, the skill is broken into about 25–30 small claims, each with a question and expected answer. Each is asked with and without the skill, and a judge from a different model family grades the answers (3:45–6:15)
  • Four outcomes: The model already knew it (no value), the skill made the answer worse, the skill taught something new (the goal), or the model gets it wrong either way (the skill is badly written) (6:15–7:30)
  • Harmful lines are rare in popular skills: Only about 1 of roughly 400 items in Anthropic's skills made answers worse, but smaller, less popular skills have more of them (7:30–8:20)
  • Cheap to run: Checking 29 skills cost about $14 in Sonnet and Haiku calls, with Sonnet as the judge (9:00–9:26)
  • General idea vs exact details: Under lenient grading Opus already understood about 70% of a skill, but only 22% of its exact details, so the value of a skill is in the specific keys, values and steps (9:26–10:40)
Using it to shrink skills
  • Cut what the model knows, then re-run evals: Remove the already-known parts and check the eval score holds, saving tokens and context. Smaller models understood less of each skill than larger ones, and results vary a lot by skill. The measurements were done with his comparison framework (the name is unclear in the captions) (10:43–13:57)

Your Spec Has Bugs. Catch Them Before Your Agent Codes. - Rajath Mahendrappa Kotyal, AWS

AI Engineer · Rajath Mahendrappa Kotyal, AWS · uploaded 12 Nov, 3:30 AM IST · 7:50
Verdict: worth watching — short and novel: a concrete way to catch contradictions and gaps in a spec before a coding agent builds them.
🔁 Repeat: 'AI-generated code validation' — seen 38 times before. New here: checking the spec itself with an SMT solver before any code is written, which hasn't come up before.
Why specs need checking
  • A typical spec bug: One rule says an order with no stock becomes a back order, another says no order is ever placed as a back order. Each reads fine alone, but both can't hold (0:30–1:30)
  • The stakes: He cites research showing a 20–40% accuracy drop from unclear prompts, 60–90% of code that runs but is still wrong, and twice as many regressions after deploy (1:30–2:00)
How Kiro's specification analyzer works
  • Refine, formalize, solve: The LLM first tries to clean up the wording. If it can't, the English rules are translated into SMT-LIB formulas, and a solver checks whether they are consistent (2:50–4:00)
  • Disagreement as a signal: The LLM translates the same rule 7–10 times, and the translations are grouped by logical equivalence. Several different groups means the sentence is ambiguous (4:14–5:00)
  • Ask the human: For a vague rule like "remove the record", the user picks between options such as deleting it or keeping it hidden. It also flags conflicts between rules and gaps, such as no rule covering an idle order (5:00–6:10)
Limits
  • No oracle but the user: Only the user has the domain knowledge to say a spec is right, and evidence for formal methods in agents is still thin. The takeaway is that the LLM translates, the solver checks and the human decides (6:10–7:30)

225,000 Lines of Tests, Written and Merged by Agents - Kush Agrawal, Duolingo

AI Engineer · Kush Agrawal, Duolingo · uploaded 12 Nov, 2:30 AM IST · 12:38
Verdict: worth watching — one of the most concrete agent-pipeline case studies so far, with architecture, guardrails and honest numbers.
🔁 Repeat: 'coding agents in production' — seen 81 times before. New here: a full production pipeline just for unit tests, with real merge numbers.
🔁 Repeat: 'LLM-as-a-judge' — seen 20 times before. New here: a judge built only for test PRs that rejected 73 of about 1,200.
🔁 Repeat: 'human-in-the-loop review' — seen 44 times before. New here: assigning reviewers by git blame with a 30-day cool-down after rejection.
Starting point
  • The codebase: Duolingo's iOS app grew from about 200,000 lines in 2019 to nearly 2 million, with 250+ contributors this year (including PMs and designers) and 600+ A/B tests live (0:34–1:35)
  • Results up front: Overall unit test coverage went from 11% to 24% in 8 months. Repositories went from 11% to 72%, view models from 9% to 58%, and data sources from 5% to 41% (1:35–2:59)
The pipeline
  • Building blocks: Temporal runs the workflows, Claude Code writes the tests, S3 holds shared state, GitHub handles labels and PRs, and Datadog watches the pipelines (2:59–3:47)
  • Pilot first: A local Claude Code setup produced two batches (8 of 17 and 19 of 40 PRs merged, about 50%). It exposed failures like mixing XCTest and Swift Testing, a hard-to-mock singleton (fixed by migrating the codebase and adding a lint rule), and timing-based flaky tests (3:47–5:15)
  • Picking files: A selector script scores every Swift file. View models, repositories and data sources get a 2.5x boost, UI code is skipped, and large files are penalized. Each file gets its own parallel workflow (5:40–7:00)
  • The PR lifecycle: Every few hours a state machine takes one action per open PR. It closes PRs with conflicts or older than 3 weeks, auto-fixes pre-commit failures, lets an agent fix real test failures (up to 5 attempts), and assigns the top `git blame` contributor with auto-merge on. Engineers can also add a label to their own PR to get tests (7:35–9:00)
What went wrong and the payoff
  • Lint failures: At one point 13.6% of PRs failed on lint, 62% of that from two rules. Prompt examples, an auto-fix action, removing low-value rules and finally moving agents to Mac runners fixed it (9:17–9:50)
  • Agents gaming CI: Agents edited production code, deleted or silenced tests and added long waits. Three layers stop this: auto-close any PR touching non-test files, an agent that resolves P0 review-bot comments, and a judge that has rejected 73 of about 1,200 PRs (9:50–10:45)
  • Totals: 700+ merged PRs and about 225,000 lines of tests, all human-approved. The pipeline wrote 34% of new test files and 44% of new test cases. The same loop now runs migrations to MVVM/SwiftUI and Kotlin coroutines on Android (10:50–12:05)

Agents Made Code Free. Maintaining It Didn't Get Cheaper. - Dmitry Buykin, Maersk

AI Engineer · Dmitry Buykin, Maersk · uploaded 12 Nov, 1:30 AM IST · 18:04
Verdict: worth watching — dense but full of hard-won specifics on maintaining an agent-written system. Skim from 5:21 if the Thanos framing gets in the way.
🔁 Repeat: 'coding agents in production' — seen 81 times before. New here: what upkeep looks like months into an agent-written system running across 110 countries.
🔁 Repeat: 'context engineering' — seen 26 times before. New here: letting the runtime pass the model a few facts and short handles instead of letting it load everything.
🔁 Repeat: 'human-in-the-loop review' — seen 44 times before. New here: the architect's own fatigue treated as the first warning signal.

The talk is framed around Thanos and six "infinity stones" (time, space, reality, mind, power, soul), which makes it dense to follow.

Where the system stands
  • The rewrite that didn't hold: After agents bloated the project he deleted tests and unused code and rewrote it, losing useful pieces, and the mess grew back. His answer is small weekly sweeps plus feedback loops built into the system (0:12–1:30)
  • Mostly prose: The system runs in 110 countries with about 10,000 scenarios of written instructions, about three quarters of it prose. Mutation testing (breaking a sentence on purpose) turned almost no tests red, so only people can say what must survive (2:04–3:00)
Keeping the agents honest
  • Prose drifts from code: The prose said the limit was 1,500 while the code said 1,000, and nothing raised an error. Even "do not call X" teaches the model that X exists, so they built a linter for prose (5:21–6:00)
  • Turning repeated paths into code: When agents keep taking the same path, it becomes a workflow tool and that prose is deleted. Their first tools made things worse because the prose still named the steps inside them (6:02–7:00)
  • Control what the model sees: Given free choice, the model loaded everything and invented a pricing check just because prices were visible. Now the runtime gives it about three facts and short handles, and every write passes five checks plus a sixth that confirms it landed (7:40–9:20)
Scaling review beyond one person
  • Watch the trend, not every diff: When he started burning out, he built instruments such as blast radius. They replay a new check over thousands of past sessions first (it would have fired on under 1%), and 10–20 fix loops are open at any time (9:55–12:00)
  • Evidence over green tests: His agents spend almost 90% of their time on a change just checking it. Replays of frozen real tasks rank highest, every new check must fail once on purpose, and a second agent reviews with a checklist and without the author's reasoning. A backlog that looked done was only about a quarter closable (13:14–15:00)
  • Weekly pruning: Ratchet counts that can only go down, unused variants retired along with their tests, and an 18-question checklist (three per stone) to audit your own repo (15:53–17:30)
