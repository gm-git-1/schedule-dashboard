We Kept Rebuilding Our AI Agent. Here's What Survived - Fuad Ali, Arize AI

AI Engineer · Fuad Ali, AI PM, Arize AI · uploaded 28 Oct, 4:30 AM IST · 20:06
Verdict: skim from 6:19 — not a rerun of his self-improving-agents talks; 6:19–15:21 packs concrete harness decisions (plan in the harness, finish gate, jq over truncated results, the 8,000-character memory file), but the testing section repeats his earlier Signal material.
🔁 Repeat: 'harness engineering' — seen 25 times before. New here: a two-year changelog of one real in-product agent (Alex), with the specific harness rules Arize kept: the plan lives in the harness, "finish" is a gated call, and there's no agent framework.
🔁 Repeat: 'agent memory' — seen 14 times before. New here: after trying vector retrieval, episodic/semantic stores and temporal knowledge graphs, they settled on one 8,000-character markdown file per user, written by a background job.
🔁 Repeat: 'context engineering' — seen 15 times before. New here: big JSON tool results are truncated and the agent uses jq to dig into them, and the trajectory is checkpointed against a fixed token budget.
🔁 Repeat: 'multi-agent / A2A' — seen 15 times before. New here: Arize rolled 10 page-specific specialist agents back into one agent that loads skills and tools on demand.
🔁 Repeat: 'evals for agents' — seen 44 times before. New here: whole sessions can be saved as datasets and replayed from a specific turn; the rest (living fixtures, judges aligned to human gold labels) is familiar.
🔁 Repeat: 'self-improving agents' — seen 16 times before. New here: little. Signal flagging Alex's own retry loops repeats his 11 Oct workshop and 27 Oct talk.
How Alex evolved
  • Timeline: The late-2023 prototype on GPT-3.5-era models was "about 50% hallucination", so math moved out of the model into harness code early. Next came a "copilot" that routed to a set of skills through a decision tree, then an August 2025 rewrite with iterative tool calling and a to-do tool. Alex 2.0 relaunched in February 2026 with a Sonnet 4.5 default (the caption reads "Sonar 4.5"). "One Alex" shipped in June, and long-term memory came last (3:20–5:38)
  • All harness, no framework: They trained no models. Everything they rebuilt was harness code, and "the loop, the plan, the stopping rule, and the memory are all ours" (5:40–6:17)
Harness decisions
  • The plan moved into the harness: With a to-do tool, the model spent most of its calls checking items off and lost focus after 20+ iterations. They added an "in progress" marker, then had the harness render the plan as a message on every model call, then dropped the marker (any unfinished item, in ranked order, is next). They are now testing with no to-do tool at all (6:23–8:28)
  • Finishing is a gate: Treating "text with no tool call" as done broke on models that announce a step in one turn and make the call in the next, and users can bring any provider. Now there's an explicit finish call that bounces back up to three times while plan items are open, a warning one step before the iteration limit, and then a forced finish (8:32–9:41)
  • Treat big results like files: Large trace JSON is truncated in context and the agent writes jq to fetch the full data when needed (the "sticky note pointing to the book" idea). When its own trajectory grows too long, the harness makes the model write a checkpoint and drops what it replaced, within a fixed history token budget (9:42–11:51)
  • One small file beat a knowledge graph: Long-term memory is one markdown file per user, capped at 8,000 characters and loaded on every request. A single background job writes it after the session ends, so it's easy to audit and to keep from mixing in other users' data. "A very good lesson on not over-engineering" (12:19–13:29)
  • One agent, not ten: A trace-analysis agent in 2025 grew into 10 specialists, one per page (for example a dataset sub-agent for synthetic data). They rolled that back to one agent that loads skill instructions and tools on demand (13:33–14:09)
  • Newest model isn't the default: They default to "fast and good enough" and put the effort into the harness. They're exploring per-task auto-routing and small post-trained models for narrow surfaces; some features, like the AI filter, need just one small-model call and no loop (14:16–15:21)
Testing and what survived
  • Production sessions as tests: Alex's live traces (still named "Copilot prod") feed regression datasets, whole sessions can be stored and replayed from a specific turn, and Arize experiments A/B harness changes. Bugs show up as 43 identical tool calls in one turn or a 227-second response rather than as errors. Signal now does most of the trace reading, while judges stay aligned to human gold labels (repeat) (15:28–17:43)
  • Six things that survived: Tracing everything, math and data computed in code and exposed as tools, golden datasets in CI, errors with an obvious fix, streaming and persistence, and skills as "a capability around an external system". Speed versus quality is still a human call (17:57–19:10)

Stop Giving Your Agent Tools. Give It a Sandbox - Mikyo King, Arize AI

AI Engineer · Mikyo King, head of open source, Arize AI · uploaded 28 Oct, 12:30 AM IST · 14:38
Verdict: worth watching — short, the first code-mode talk in the history, with an honest list of costs and measured savings; skip 11:44–12:50 if you saw yesterday's Harbor talk.
🔁 Repeat: 'sandboxes for agents' — seen 18 times before. New here: the first talk in the history on "code mode", where the agent searches for tools and composes them in code inside a sandbox instead of calling them one by one.
🔁 Repeat: 'context engineering' — seen 15 times before. New here: code mode as the fix for context bloat, with only the needed slice of tool output going back into context.
🔁 Repeat: 'evals for agents' — seen 44 times before. New here: only the result. The Harbor setup repeats Xander Song's walkthrough yesterday, but the before/after numbers (43% fewer tokens, 31% lower cost) are new.
🔁 Repeat: 'secrets management' — seen 7 times before. New here: only briefly, as one of code mode's costs (secrets used in the sandbox must never reach the context window).
Why code mode
  • The pitch: Software used to split into tools for engineers, who could script "get every invoice out of my inbox" in about 50 lines, and tools for everyone else. Claude Code-style agents dissolve that line, and models are trained for it (SWE-bench), so build agents that write the software they need (0:36–1:48)
  • What it is: Classic agents load a big tool catalog and push every raw result into context, which brings context rot, pagination, many turns and compaction. Code mode lets the agent search for the tool it needs and run it in a programming environment (sequentially, in parallel or with conditionals), calling many tools in one turn and returning only what's needed (1:52–4:34)
  • Why it works: Progressive disclosure of tools, composability (he points to Claude's dynamic workflows), token efficiency, and emergent tool-building. For example, the agent can strip PII from records in code instead of reading credit card numbers into its context (4:38–6:07)
How Phoenix does it
  • Four surfaces: Bash, which composes grep and sed with Phoenix's CLI and offloads output to files; a Python sandbox with all of Phoenix's REST CRUD endpoints exposed in it; SQL for aggregate questions like "LLM spans with P95 latency of X" (the SQL tool is a partial repeat of yesterday's Harbor talk); and a UI-bound programming layer in a web worker with two-way data binding to the browser, so the agent can change time ranges and read front-end data, which he likens to computer use (6:11–8:17)
Costs and open problems
  • Hidden costs: Sandbox CPU, memory and lifetime, network egress, keeping secrets out of the context window, and permissions that are fine for five operations but too broad on the sixth or once composed. Sandboxes don't always boot, code is harder to debug than single tools, the tool parameter is now code, tool discovery needs a handshake, and running code mode in both MCP and the harness causes double sandboxing, with serialized JSON passed between them (8:19–10:38)
  • Open problems: A long script that fails midway can't resume, language choice matters for math (LLMs are good at JavaScript, but it's weak at math), images and binaries need something like a signed handoff out of the sandbox, and smaller cheaper models aren't as good at code mode (10:42–11:42)
Results
  • Harbor eval: Agents run in sandboxes with network access off, over multiple trials, with verifiers scoring 1 or 0 and pass@k tracked per task (repeat) (11:44–12:50)
  • Numbers: Before vs after code mode: 43% fewer tokens, 31% lower cost and roughly flat latency despite sandbox overhead, across Claude Code, MCP and CLI surfaces. Trajectories plus evals let a coding agent hill-climb the instructions when a new tool first lowers efficiency (12:52–13:55)

What a $900M Bank Error Teaches Us About AI Agents - John Feminella, Two Sigma

AI Engineer · John Feminella, AI architecture and engineering, Two Sigma (views his own) · uploaded 27 Oct, 8:30 PM IST · 18:56
Verdict: skim — the Revlon story (1:03–5:21) is a great watch, but the five controls stay at framework level, with no implementation details or numbers.
🔁 Repeat: 'agent governance' — seen 8 times before. New here: a five-part control stack from a hedge fund (registry, risk-scored review, purpose-declared tool access, shared firm-wide evals, approval classifiers), each built so low-risk agents don't queue behind risky ones.
🔁 Repeat: 'AI in regulated industries' — seen 15 times before. New here: the Citi/Revlon $900M payment error as the case for controls that don't lock everything down.
🔁 Repeat: 'human-in-the-loop review' — seen 18 times before. New here: conservative classifiers handle routine approvals and only ambiguous calls reach a human, illustrated by an agent that lost its "wait for my approval" instruction during context compaction.
🔁 Repeat: 'agent security' — seen 22 times before. New here: tool and endpoint access derived from the agent's declared purpose in the registry and enforced at start-up. This is close to the intent-based authorization covered in the Keycard talks.
🔁 Repeat: 'evals for agents' — seen 44 times before. New here: only the organisational angle, one shared firm-run eval approach so teams write only "what's true about your agent".
The Revlon story
  • What happened: In August 2020, Revlon owed about $8M of interest on a 2016 term loan split across 300+ lenders, with Citibank as administrative agent. In Citi's Flexcube software, the easy way to book this was to pretend Revlon was repaying the whole loan, with the principal sent to an internal wash account. The wash-account boxes weren't checked, the "money is leaving the bank" warning looked expected because interest was going out, three approvers signed off, and about $900M of principal went to the lenders (1:05–4:12)
  • The aftermath: Lenders holding debt that traded at around 60 cents on the dollar refused to return the money, and loan agreements started adding clauses against this. His lesson is that the procedure and controls existed and "everybody did what they thought the right thing to do was" (4:14–5:21)
  • Framing: Agents are non-deterministic, but so are humans, and firms give people autonomy plus boundaries rather than locking them in rooms. Full sandboxing is safe but useless, letting agents run wild is too weakly isolated for regulated firms, and policy documents in prompts can't be enforced at runtime (5:23–7:22)
Five composable controls
  • 1. Agent registry: Agents (chatbots, "Frankenstein" MCP mashups, notebooks, web tools) record their owner, tools, endpoints and product. Using a firm-approved agent framework registers them automatically, and humans, programs and other agents query the registry to discover what exists. A heavy register-before-running gate would just push people to shadow IT (7:34–9:42)
  • 2. Risk-based review: A Jira-ticket summarizer shouldn't wait two months for the same sign-offs as a production deployment agent. Most enterprise agents are purpose-built, unlike open-ended ones such as Claude Code or Pi, so their declared tools, endpoints and controls can set the level of review (9:46–11:40)
  • 3. Tools follow purpose: A blanket short allowlist is "safe, but it's also useless". Instead the author declares the four tools they need out of the 500 available; for example, a research summarizer gets web access and a release deployer doesn't. In managed environments the agent looks up its policy in the registry at start-up, and it's turned into enforceable endpoint and host rules, with no IT tickets (11:43–14:42)
  • 4. Shared evals: Evals are treated like unit tests, because the model is a runtime dependency. A central committee sign-off would queue every prompt tweak, so the firm runs one shared eval approach and teams just write what's true about their agent (14:46–16:14)
  • 5. Ending approval fatigue: Approving every action leads to reflexive "yes". His example: earlier this year an AI-lab director's OpenClaw agent compacted its context, lost "wait for my approval", deleted hundreds of emails and ignored her stop command. The fix is deterministic fast paths for explicit rules, conservative classifiers for routine calls, a human only for ambiguous ones, and outright denial for clearly dangerous ones; anything approved 99.99999% of the time should become a rule (16:17–18:04)
  • Why cars have brakes: "So that you can go fast and stop safely" (18:06–18:41)

Why Are We Still Governing AI Agents Like Software? - Tim Tyler, Gravitee

AI Engineer · Tim Tyler, Gravitee · uploaded 27 Oct, 2:30 PM IST · 18:13
Verdict: skim from 8:18 — the scope-intersection example and the confidence-based recourse ladder are the only concrete new bits; the rest is a framework pitch over well-covered agent-governance ground.
🔁 Repeat: 'agent governance' — seen 8 times before. New here: Gravitee's three-stage "Agent Accountability" framework (Assignment, Alignment, Administration) with published audit controls at agentaccountabilityframework.org; the "judge agents like employees" framing itself echoes Druid AI's scorecard and Michele Grant's trust framework.
🔁 Repeat: 'agent identity' — seen 5 times before. New here: only the basic ask (one unique ID in one shared registry, tied to a named human sponsor), no protocol or implementation.
🔁 Repeat: 'human-in-the-loop review' — seen 18 times before. New here: confidence thresholds that decide when to redact, escalate to a human or block.
Assignment: who the agent is and who answers for it
  • The hook: A joke job ad (no ID, no manager, shared passwords, works 24/7, never fired) that nobody in the room would accept, which he says is how companies are already deploying agents (0:32–1:07)
  • Identity, team, sponsor: Every agent gets one unique ID in a single shared registry that everything else points to; it is a teammate that takes and gives back team context, "not a digital clone" of you; and it has a named human sponsor ("Sven") who defines its purpose, owns its cost and gets the call when it goes wrong — "I have the agent" (3:12–5:55)
Alignment: role, mission and scope
  • Role vs mission: The role (purpose, responsibilities, budget, what success looks like) is set at onboarding by the sponsor and rarely changes; the mission, a term he borrows from the new AAuth work, is what the agent is doing at this moment, e.g. per MCP tool call, and the agent defines it (repeat) (6:26–7:27)
  • Delegated scope only shrinks: Sven can access A–D, agent 203 has C–D, agent 409 has D–F; when 203 delegates to 409 on Sven's behalf, 409 may use D, E and F to do the work but can only return D, the intersection along the chain (8:18–9:32)
  • Never assume alignment: Model alignment, team context and outside agents (treat them like contractors with their own ID and access) are inherited and outside the sponsor's control; what he controls is deterministic rules (the floor, like FGA policies) plus probabilistic intents, which together form the agent's contract (9:34–11:12)
Administration: oversight and recourse
  • Scorecards and guardian agents: "Behaving" (staying inside authority, e.g. only invoices up to $40,000) is not "succeeding" (invoice-match accuracy, reconciliation cycle time); rules are checked, intents are judged with a confidence level, and guardian agents watch the model, incoming context and output at machine speed, because a quarterly review is "4 million decisions too late" (repeat) (11:55–14:19)
  • A recourse ladder: Intent confidence maps to actions (around 90% confident: redact; under 50%: escalate to a human; under 20%: block), while rule breaches escalate from restricting authorization, to suspending access after five violations in a day, to suspending the agent after days of it; start strict and loosen with repeated success, with the sponsor acting as coach who tunes rules and authority (15:00–17:01)

300 Agents, 60 People: How We Secured Our Own AI Agents - Aiden Sochowski, Runlayer

AI Engineer · Aiden Sochowski, founding engineer, Runlayer · uploaded 27 Oct, 1:30 PM IST · 16:38
Verdict: skim from 8:55 — the session-intent classifier, history-based de-scoping and cost anecdotes are the new parts; the injection examples rehash well-covered ground and the talk stays high level.
🔁 Repeat: 'agent security' — seen 22 times before. New here: findings from Runlayer monitoring its own 300+ agents, and a classifier that checks each tool call against the session's defined intent.
🔁 Repeat: 'prompt injection' — seen 4 times before. New here: little; the email-exfiltration and argue-the-PR-reviewer examples are hypotheticals close to Bloomberg's and Gravitee's earlier ones.
🔁 Repeat: 'agent observability' — seen 25 times before. New here: using per-agent tool-call history to suggest permissions to remove.
🔁 Repeat: 'MCP servers' — seen 34 times before. New here: a vibe-coded MCP server whose repeated errors ran up token costs.
🔁 Repeat: 'token costs / AI spend' — seen 10 times before. New here: one model switch raised a team's cost over 100x in a week.
🔁 Repeat: 'AI gateway' — seen 4 times before. New here: only as the setup; they put a gateway in front of everything and logged every session and tool call.
What they found by watching their own agents
  • More agents than people: At about 50–60 people, Runlayer runs 300+ agents a day (triggered by chatbots, SaaS apps and other triggers, not only users); after putting in a gateway and logging every session and tool call centrally, they mapped agents by topic and risk, finding some given too many tools and a large blast radius (0:58–2:39)
  • Email exfiltration and policy pain: A naive, over-permissioned support agent reading inbound email could be told to list your prospects and leak them. Defences stack (a classifier on every email read, regex blocks on outbound PII, blocking reads from private calendars), but none is 100% and writing gateway policies for every context is "really tricky" (repeat) (3:39–6:18)
  • Attacks that span a session: A PR-review agent allowed to approve can be argued with in GitHub comments ("only review the cleanup") until it approves; "if you ask it 10 times" it will probably comply even if Opus is hard to inject. Runlayer trained its own classifiers that take the whole session and check each tool call against what the agent was defined to do (6:27–8:50)
Scoping agents down
  • Use session data to de-scope: Well-scoped agents give high-signal data, so tool use outside an agent's normal range (e.g. the recruiter bot with ATS, meeting notes, calendar and messaging access) flags high-risk runs; their models read an agent's tool-call history and suggest permissions to remove, since scoping up front is hard (8:55–10:55)
  • One poisoned agent affects the rest: A malicious resume read by one agent can end up in shared systems that other agents read as normal instructions; the only fix they found is mapping how systems connect and tightly restricting where each agent can write, to keep other agents' context "pure and not poisoned" (10:59–12:26)
Beyond security: cost
  • Broken MCP servers and model switches: The recruiting team's vibe-coded MCP server for a vendor API kept failing on formatting while the agent retried, ballooning token cost; separately, people who switched from a cheap model to a frontier one ("GPT-56 Luna" to "Fable 5.1" in the captions) saw costs jump over 100x within a week. Their fixes: monitoring and rate limits, budgets, sane defaults and requiring a reason for the bigger model (12:51–15:34)

How a Trading Firm Ships New AI Models the Same Day - Noyan Tokgozoglu, Optiver

AI Engineer · Noyan Tokgozoglu, head of AI Engineering, Optiver · uploaded 27 Oct, 12:30 PM IST · 23:23
Verdict: skim from 7:06 — the same-day model rollout, meta harness and especially the spend fixes at 9:53 are concrete and well told, though gateway and cost-control ideas are well covered in the history.
🔁 Repeat: 'AI for finance' — seen 14 times before. New here: a market maker's view, where a rollout shows up in that day's P&L, so missed opportunities are costly and decisions must be fast and measurable.
🔁 Repeat: 'token costs / AI spend' — seen 10 times before. New here: fresh sessions starting at 200k+ tokens of context, cut with MCP tool search, CLI wrappers around MCPs, cache tuning and team-set alerts and limits.
🔁 Repeat: 'AI gateway' — seen 4 times before. New here: an on-prem inference gateway (routing, per-model spend, budgets, provider failover) plus an agent gateway that acts as a single ledger of every agent.
🔁 Repeat: 'harness engineering' — seen 25 times before. New here: a "meta harness" layer where teams define portable harness configs across several supported harnesses.
🔁 Repeat: 'evals for agents' — seen 44 times before. New here: replaying tool calls through an MCP proxy with a per-call confidence for how well its world state can be restored to that point in time.
🔁 Repeat: 'LLM releases / benchmarks' — seen 42 times before. New here: not model news but the process of benchmarking each new frontier model on internal golden sets the day it ships.
🔁 Repeat: 'vendor lock-in' — seen 4 times before. New here: they left an inference-gateway vendor that put needed features "on the road map".
Why a trading firm moves fast
  • P&L in hours: Optiver makes 10M+ trades a day pricing 1M+ instruments across 10+ offices; the balance sheet is zeroed each morning, so a change rolled out to traders and quants shows its P&L impact within hours, unlike his Apple experience of quarters. Missed opportunities (e.g. a hypothetical SpaceX AI IPO) are costly, hence a bias for action (0:26–2:51)
  • Platform principles: Be modular for each new model or paradigm (loops, swarms, graphs), measure at every layer with internal benchmarks because their data differs from public ones, be self-service with good defaults for high-agency traders, forward-deploy AI engineers to sit with traders, and run everything on-prem; only third-party inference leaves, under zero-data-retention agreements (2:54–5:08)
The platform
  • Stack: Third-party and self-hosted open models sit behind an inference gateway for routing, per-model spend, budgets and failover ("any time that we're down… we're not making money"). An agent platform has registered skills, plugins and tools plus per-team knowledge and memory, an agent gateway is the single ledger for agents and humans with shared identity management, and the surfaces are a web UI, an "agent workbench" for shareable team personas and a company-wide personal assistant (5:27–6:59)
  • Same-day frontier models: A new public frontier model is benchmarked the same day on golden sets collected with partner trading teams, then wired into the gateway with cost controls and updated harnesses, backed by follow-the-sun support rotations and a recommendation note to staff (7:06–8:26)
  • Model- and harness-agnostic: Some workloads must run in a fully on-prem DMZ, so everything goes through the gateway, every model interaction is logged into the eval system, and a meta-harness layer lets teams define portable harness configs that plug into their knowledge base, with knowledge mined from traces over time (8:30–9:48)
Getting spend under control
  • What fixed it: Spend jumped at the December "Claude Code moment" and again with the summer's frontier releases, then came back under control. Fresh sessions were loading 200k+ tokens of context by default, so they added MCP tool search, CLIs wrapping MCPs, cache-invalidation and TTL tuning, and moved content from huge system prompts into the knowledge base; these savings grow as tokens get pricier (9:53–12:11)
  • People manage their own budgets: Showing teams their spend and letting them set their own alerts and limits worked ("they actually do a pretty good job"), along with open-weight models that compete on token cost, routing to cheaper models, frontier-plan/small-model-implement splits and better retrieval; "this is just about getting more ROI out of the same tokens" (12:26–13:50)
  • Meet users where they are: Instead of people's hacky web UIs and bespoke dev-box setups, they built a portal (sessions, chat, artifacts) that traders now send PRs to, adding collaborative editing, multiplayer rooms mixing people's agents and a Slack client (13:54–15:30)
Q&A
  • Eval replay and agent sprawl: Every tool call is OTel-logged into evals, but replaying, say, a Slack support bot on a new model needs past world state. Backtest data is easy to query at a point in time and Slack isn't, so each call gets a confidence score for how well it can be replayed through a proxy around the MCPs. Rather than merging agents into one bloated agent, they version agents and scope each to one measurable task that others call through the agent gateway. On build vs buy, vendors were slow to support on-prem and tend to lock you in (19:37–21:09), (21:36–23:13), (17:20–18:33)
