Build the Workshop Before the Software Factory — Armin Ronacher, Earendil

AI Engineer · Armin Ronacher, Earendil (Pi coding agent) · uploaded 23 Nov, 1:30 AM IST · 19:56
Verdict: worth watching — the topic is well-worn, but the 20 minutes are full of Ronacher's own usage data and practical habits you haven't seen in the earlier software-factory talks.
🔁 Repeat: 'human-in-the-loop review' — seen 52 times before. New here: Ronacher's own session data on how far he has stepped back, and his trick of having the agent write an executive summary before verification instead of reading the code.
🔁 Repeat: 'software factory' — seen 27 times before. New here: the counter-pitch (build the workshop first, then the factory) backed by his numbers: 141 projects started, only 10–15 still maintained.
🔁 Repeat: 'harness engineering' — seen 43 times before. New here: the claim that Pi's core harness hasn't changed in a year and still does far more, purely because the models improved.
🔁 Repeat: 'decision models' — seen 11 times before. New here: using cheap classifier models as the if-branches inside code-mode workflows, e.g. triaging 3,000 support tickets.
🔁 Repeat: 'durable execution' — seen 4 times before. New here: suspending agents and their sandboxes to wait out cheaper flex-scheduled tokens.
The models improved, the harness didn't
  • Same tools, much more power: Pi's core harness has the same tools as last December, yet it does far more because the models got better. Old harness tricks have mostly stopped mattering: his favourite plugin, PyAutoResearch (drive toward a goal like better performance), is no longer needed with current models. His own count of corrections per session dropped with each new model (1:43–3:17)
  • Tasks now run 14 minutes: At the 90th percentile, an agent ran about 2.5 minutes per task with Opus 4.6 last December and now runs 14+ minutes. Current models also reach for Bash far more than any other tool, and code mode is slowly creeping up in his data (3:17–4:47)
Human attention is the limit
  • Flat prompts, exploding agent time: He still sends a fairly flat 120–190 prompts a day, but agent run time went from less than his working day to many times it. He warns that GitHub and older websites are being hammered by agent traffic they weren't built for (4:47–6:17)
  • 141 projects started, 10–15 maintained: Repos he created keep climbing, but projects he commits to regularly have stayed at 10–15. A friend fully automated an open source project with an auto-review agent, then turned it off once he stopped caring and wanted the tokens for other work (6:17–7:47)
  • Know when to push back: Agents are rewarded for finishing the goal, which easily produces a "Simpson car" of bolted-on features. He calls the difference "true skill vs agent skill": his son, who isn't an engineer, sends him PRs through the same setup, and the quality gap is obvious (7:47–10:02)
  • Executive summaries instead of reading code: Around 70% of the way through a session, before verification, he has the agent write a short executive summary and a typeset HTML page explaining what it did. That is how he keeps understanding his projects now that he often doesn't read the code (10:02–11:32)
Toward excellent software
  • Uncontrolled growth and file formats: When every agent can implement any format, implementations drift. His example is a tar archive crafted so different tar implementations read it differently. Open protocols and shared file formats matter more than ever, and forking is replacing upstream collaboration in open source (11:32–15:17)
  • Durable agents: Long-running overnight agents need to suspend, resume and restart themselves. That also lets them pause, sandbox included, while waiting on discounted flex-scheduled tokens that can take minutes to arrive (15:17–16:51)
  • Code mode plus classifiers: Following Cloudflare's idea, the agent gets JavaScript to call its tools, so the harness (Codex and Pi already support this) can run large batches of tool calls outside the context. Combined with cheap, fast classifier models as the decision points, it can triage something like 3,000 support requests in minutes instead of hours (16:51–19:06)

TanStack Just Shrunk React by 70%

Better Stack · Better Stack · uploaded 23 Nov, 3:00 AM IST · 7:01
Verdict: worth watching — a short, honest test: smaller bundles and faster loads, but slower typing on heavy UIs.
🔁 Repeat: 'JS/TS ecosystem' — seen 16 times before. New here: TanStack Redact itself, a React replacement for the browser, tested with real bundle and keystroke numbers.
What Redact is
  • Drop-in React for the browser: TanStack Redact replaces react and react-dom in the browser while you keep your normal React imports, components and hooks. You add one build plugin, and it works with TanStack Start, Vite, Next.js, Webpack and Rspack. On Next.js, real React still runs on the server and handles server components (0:18–0:46)
  • The 70% claim holds for small apps: On a fresh Vite React starter, gzipped JS went from 66.8 KB (React 19) to 20.2 KB with Redact, or 12.9 KB with the "nano" preset. TanStack's own tests cut total client JS + CSS by 70.5% (Vite), 43% (TanStack Start) and 28.5% (Next.js). In his tests it saved about 46 KB no matter the app size, so the percentage shrinks as your app grows (0:46–1:41)
  • How it gets small: A build-time alias swaps the imports. Redact drops React's concurrent scheduler and renders synchronously, so a heavy render can delay input. Build flags can strip context, suspense, memo or hydration, and deprecated APIs like findDOMNode are gone (1:41–2:36)
  • Why not Preact: Preact's compat layer is smaller (11.2 KB vs Redact's 23.3 KB), but it has drifted from React 19. It lacks useActionState, useOptimistic and useFormStatus, and its useTransition pending state is always false. Tanner gave up after about five patches (2:36–3:26)
Real-world results
  • Mixed production numbers: On Tanner's blog, JS dropped by a third and first paint was about 18% faster. On tanstack.com, JS only dropped about 5%, and server-component pages showed their main content 8–43% later. PostHog's coding agent measured a 3.6% saving with 33 of 95 sample test files failing, and concluded "do not adopt now" (3:26–4:19)
  • His 20,000-order dashboard: With the CPU throttled 4×, the Redact build had no errors, 17% less JS and a 14% faster first paint. But the slowest keystroke in search went from 80 ms to 200 ms, and it was still 168 vs 200 ms with React's concurrent feature off. TanStack's own list benchmarks score React 100 and Redact 78 (4:19–5:37)
  • Built by prompting: Tanner built the first version in "one day of prompting with Claude", and it now passes 1,859 tests. In August he called it a "slop fork" of React on the Better Stack podcast. Now TanStack thinks it is worth maintaining (5:37–7:01)

This Tiny Chip Trained Its Own AI in 18 Seconds

Better Stack · Andres, Better Stack · uploaded 22 Nov, 12:45 PM IST · 10:07
Verdict: worth watching — a fun, concrete hardware demo with real numbers; a genuinely new angle (on-chip training) on the edge-AI topic.
🔁 Repeat: 'edge / on-device AI' — seen 4 times before. New here: the chip trains the network itself (backprop + Adam), not just inference, and learns new sounds in under a second.
The setup
  • Inspired by a laptop-trained experiment: Bill McCartney's post "Neural nets on chips that 'can't do' neural nets" trains a small classifier (sine, square, chirp or noise from 32 sensor readings) on a laptop. It then runs the weights on 16 microcontrollers, down to an 8-bit PIC16 at about 2.3 decisions a second. Andres moved the training onto the chip (0:47–1:37)
  • How small it is: The network goes 32 → 32 → 16 → 8 → 4, with 1,756 weights (about 7 KB). 80 Adam training steps add up to about 1.32 billion multiply-adds at 240 MHz (1:37–2:32)
  • Memory is the real limit: Training needs about 28 KB for gradients and Adam state plus 128 KB for examples, which fits the ESP32-S3's 512 KB internal RAM and FPU. The training engine is about 250 lines of plain C with no TensorFlow Lite. The hardware is an ESP32-S3 board with 8 MB PSRAM, a 1.28" display, an INMP441 mic and one button (2:32–3:30)
Demo 1: retraining the signal classifier
  • Same accuracy as the laptop: The board generates its own 4,096 training examples at boot, bit-identical to a Python generator. It goes from about 25% (guessing) to 84.8% test accuracy, exactly what NumPy gets (3:30–4:26)
  • Speed: Training takes 35.1 s on one core and 18 s on two (1.95× faster), versus 0.08 s in NumPy on a laptop (about 220× faster). Inference runs at 20,488 decisions/s at 6.9 cycles per multiply-add, versus 36 in Bill's table. That's about 5× faster, from compiler speed flags and keeping weights in fast internal RAM, without SIMD (4:26–5:44)
Demo 2: learning his own sounds
  • Trained in 0.9 seconds: When a sound is louder than the background, the board records half a second and turns it into a 161-number pitch-over-time picture. He recorded 10 examples each of a clap, a finger clap and a table tap, and the board added time shifts and noise. It trained on those 30 examples for 40 rounds in 0.9 s, all on the chip (6:11–8:45)
  • Results and limits: It usually identifies the sound with high confidence, but sometimes confuses a clap with a finger clap, since both are short high-frequency bursts. The networks are tiny and the signal processing does a lot of the work. Still, training on-device is practical for small, specific decisions, like a sensor learning what one machine normally sounds like (5:44–6:11) (8:00–10:07)
