From 15% to 90% GPU Utilization: Fix the Data Pipeline, Not the Model

Tarun Sunkaraneni, Amazon AGI · 10 Oct, 7:00 AM IST · 17:01

No repeat flag. This is the first data-loading/throughput talk in the history, with step-by-step numbers.

The problem:

Fixes, one at a time:

At scale:

Verdict: worth watching. It's the most concrete talk today; if short on time, start at 5:18.

  • CPU work starves the GPU: Multimodal preprocessing (PIL resize/normalize, audio cropping) is CPU-heavy. Clusters have far more CPUs than GPUs, but the GPU is still the part left idle. (1:56–2:37)
  • Wait-time ratio: He measures (data prep + transfer) ÷ (prep + transfer + train). The baseline spends 85% of its time waiting on data, so GPU utilization is only 15%. The target is 90%. (2:37–3:37)
  • Baseline: A Qwen3-VL-style model is trained on JSONL with images in S3, feeding Megatron data-parallel ranks. Serial fetching for a 256-item batch means a 15–20 s train step waits on more than 100 s of data loading, and the flame graph is mostly S3 loads. (5:18–6:33)
  • Concurrency matched to the bottleneck: asyncio handles the IO-bound image fetches and Ray actors handle CPU processing. Threads only help for ops that release the GIL (HF tokenizers, PIL transforms, some pandas). Per-batch fetch time drops to about 40 s, a 25% speedup. (7:10–9:04)
  • Prefetching: A background thread keeps a queue ahead of the trainer, so data fetch time per batch is close to 0 s. The costs: checkpoint/resume gets trickier and there's a cold-start fill period. (9:04–10:35)
  • Zero-copy with Ray's object store: Each sample (megabytes of image tensors) was pickled worker→coordinator→trainer and could cause OOMs. Passing object refs instead takes the wait ratio from 85% to 20%. (10:35–12:47)
  • NIC bottleneck: With 4× DP ranks, 200 data streams and 4× batch size, the wait ratio went back up. Ray places workers on the same node by default, which saturates that node's network card. Spread scheduling plus zero-copy retrieval did nothing at small scale but together gave +50% throughput at scale. (12:47–15:35)
  • Lessons: Fixing one bottleneck exposes the next (throughput → wait time → memory → retrieval cost). Test configs at several scales, and profile the baseline first. (15:35–16:33)

Small Models, Big Results: Training a Finance Agent for Under $500

Charles (research scientist), Snorkel AI with UC Berkeley Sky Computing Lab · 10 Oct, 6:00 AM IST · 17:15

No repeat flag. It's a full RL recipe with costs and ablations.

Headline result:

How the data was built:

Training setup:

Results and ablations:

Verdict: worth watching. The last 2.5 minutes from 14:40 are eval-axis philosophy and a grants/hiring pitch.

  • 4B beats 235B: An RL-trained Qwen3-4B gets about 60% pass@1 on financial tasks, against 51% for Qwen3-235B. Scripts and synthetic data are open on GitHub. (2:29–3:26)
  • FinQA from 10-Ks: SEC 10-K filings were pulled from EDGAR and Qwen3-30B extracted about 6,900 SQL tables, with one QA pair per table built from an expert question taxonomy. Verification has three layers: programmatic lineage/column checks, independent agent review, then expert manual review. The split is 4,000 train / 500 val / 290 held-out, with no company appearing in more than one split. (4:55–7:11)
  • Frontier failure modes: Schema hallucination (made-up tables/columns), context flooding (SELECT \*), and poor error recovery (the 235B model retried the same failed strategy). The same issues showed up in their insurance-underwriting work. (7:11–8:08)
  • rLLM + GRPO: Berkeley's rLLM framework works with any agent framework through a decorator, with near-zero code changes. It has GRPO and other RL algorithms built in. (8:08–9:04)
  • Cost breakdown: A ReAct agent with table tools, binary correctness reward from a GPT-5 nano judge (reference-based), about 1,000 concurrent environments, 8× H100. Total under $500: about $420 compute and $40 for the judge API. (9:04–10:21)
  • Generalizes, doesn't erode: Base accuracy more than doubled. Gains carried over to a multi-table set (2–5 tables, 1,000/120/80) without any multi-table training, and BFCL general tool-calling scores went up slightly. (10:21–12:34)
  • Simpler won twice: Training only on simple single-table data beat both mixtures and a single→multi curriculum. A binary reward beat an expert-designed weighted rubric with intermediate rewards. His takeaway: "the bottleneck was never reasoning depth, it was tool use." (12:34–14:04)

Why Your Company Needs a Context Graph

Gil Feig, Merge · 10 Oct, 5:00 AM IST · 15:11
🔁 Repeat: 'MCP servers' — seen 9 times before · 🔁 Repeat: 'agent memory' — seen 6 times before

New here: a concrete rule for when to use a cached copy versus a live lookup (freshness SLAs) and a provenance checklist. The rest is familiar architecture.

What and why:

How to select context:

Traceability:

Verdict: skim from 3:15 to about 13:24; everything from 14:22 is a Merge product pitch.

  • Company brain (repeat): The context graph combines third-party data (NetSuite, Jira), structured context, memories and skills. (2:18–3:15)
  • Where live MCP lookups break: "Why was customer A upset?" works over Zendesk MCP. "Which customers were upset last year?" means paging 100 tickets at a time until it times out. Vendors have no reason to offer semantic endpoints, so you sync a copy into a vector DB and keep live MCP for point lookups and actions (e.g. Stripe). (3:15–5:56)
  • Router + summarizer: A router sends the prompt to the right place, and a summarizer merges synced and live results so raw dumps never reach the agent. (5:56–6:47)
  • Skills first (repeat): What "upset" means is company-specific. One company may count tickets, another may check Qualtrics surveys first. So the agent checks skills and memory before fetching data. (6:47–8:35)
  • Four tiers and their costs: Prompt/skills/memory; live API calls (cheaper, easier); cached/synced data (needed for semantic queries but expensive and goes stale); and "derived context", i.e. stored summaries so common questions aren't re-fetched. (8:35–10:07)
  • Selection flowchart: Check for a skill/memory match first. Then use the cache if it's within your freshness SLA, otherwise call the live API. Loop until there's enough context, optionally write a memory, then respond. (10:07–11:21)
  • Provenance checklist: Record where and when data was fetched, under what ID and scopes, who accessed it, with what permissions, whether it was transformed, and what invalidates it (e.g. older than a month). In the Acme example he caps live ticket pulls at 5 to avoid timeouts. (11:21–13:24)

Generation Is Cheap, Review Is Expensive: How to Stop Shipping AI Slop

Gabriel Martinez, G2i · 10 Oct, 1:30 AM IST · 17:17
🔁 Repeat: 'AI-generated code validation' — seen 7 times before

New here: little. It's an opinion essay with no data. The fresh bits are "diagrams as a compressed review surface" and the convention-over-configuration argument for agents.

The argument:

What to do instead:

Verdict: skim from 12:23 for the ~3 minutes on diagrams and conventions; skip the rest if you've seen the earlier code-validation talks.

  • Definition: Slop is "output that looks finished before the thinking is finished." The danger is less a bad machine choice than the engineer never noticing there was a choice to make. (0:39–1:54)
  • Lines spent (repeat): He cites Dijkstra's "lines spent, not lines produced". Agents don't rescue a big ball of mud, they make it bigger faster, and the result is bloated B2B-style UX. (3:47–5:37)
  • Prototype illusion: Stakeholders take an hour-long vibe-coded prototype as proof the hard part is done. He quotes SQLite's creator: a PR isn't free, it's a request for 25 years of maintenance. (5:37–7:24)
  • Bad incentives (repeat): Pressure to merge fast leads to unreviewed merges (he admits doing it). Multi-thousand-line PRs can't really be reviewed, and 10 bullets of scope come back as a 20-page doc. "Generation is cheap, evaluation is expensive." (7:24–10:32)
  • Compressed review surfaces: Diagrams of service boundaries, data flows, state transitions and failure modes, plus declarative code that pushes implementation detail to the leaves, so humans review the shape of the system. (12:23–13:19)
  • Conventions over choices: Agents produce five plausible patterns in five styles unless conventions narrow the options. Rails is his example: he came back after 4 years and the same patterns still held. Ecosystems with one right way work better for agents. (13:19–15:32)
  • ORC pitch: G2i's ORC builds planning, review, adversarial checks and context management into the workflow. No specifics or results are given. (15:32–16:48)

From Context to Memory: Your Agents Need a Real Memory Layer

Anders Swanson, Oracle · 10 Oct, 12:00 AM IST · 18:20
🔁 Repeat: 'agent memory' — seen 6 times before (and Oracle's third memory talk, after Kay Malcolm on 14 Sep and Ignacio Martinez on 18 Sep)

New here: the write-path order (redact before embedding) and a clear list of memory failure modes. The framing and memory types are well-worn.

Familiar ground:

The concrete parts:

Verdict: skim from 12:24 for the failure modes and feedback loop; the rest repeats earlier memory talks.

  • Context windows aren't memory (repeat): Bigger windows lose the useful signal to compaction. Markdown scratchpads and grep don't scale to multi-tenant setups, and "you're going to be building your own database." (0:57–2:46)
  • Converging pattern (repeat): Formation, hybrid recall, consolidation, time-awareness, feedback and governance. Memory types are episodic, semantic, procedural and working state. (2:46–4:36) and (6:11–7:23)
  • Storage schema: ID, content, JSON tags, vector embedding plus vector index, full-text index, graph links between memories, temporal validity/last-used, and audit events (who created and used it). (7:23–8:17)
  • Write path order: Redact PII and secrets first, before embedding or enrichment. Then enrich, scope (agent/team/org), embed, and link an "episode" (the transcript slice that produced it) for provenance. (8:17–10:04)
  • Hybrid recall (repeat): Vector, keyword, entity, graph and feedback branches with tunable weights, fused into a top-K "context card" that shows per-branch scores. Facts can use exact-ID match instead of similarity. (10:04–12:05)
  • Failure modes: Stale memories (e.g. switching from npm to another build system), bad scoping (seeing another user's history), poisoned memory from prompt injection, conflicting memories that both rank high, over-recall crowding the context, leakage, and silent drift that appears at 50k–1M records. (12:24–15:25)
  • Feedback closes the loop: Track whether each retrieved memory was helpful, stale, irrelevant or harmful, and use that to promote or demote it. (15:25–16:18)

Designing CLIs for Agents, Not Humans

Pedro Lopez, Airbyte · 9 Oct, 10:30 PM IST · 18:20
🔁 Repeat: 'MCP servers' — seen 9 times before

New here: the CLI half (design rules for agent callers) and specific MCP client gaps: Claude Desktop doesn't support URL-mode elicitation, and Claude limits descriptions to 2 KB.

MCP lessons:

CLI for agents:

Verdict: skim from 11:07; the CLI section is the new material.

  • Thin interfaces over one platform: The MCP and CLI are presentation layers generated from the OpenAPI spec, because the platform deploys 10+ times a day. (2:52–3:50)
  • Two tools, not hundreds (repeat): Just "describe connector" (schema) and "execute" (read/write/delete), with progressive discovery, instead of one tool per entity per connector. (5:41–6:57)
  • OAuth or bust: Clients are built around OAuth; Anthropic's custom-connector setup has no field for a bearer token. Users expect mobile-app-style long sessions, so store offline sessions separately from the web app. (6:57–8:35)
  • Elicitation isn't usable yet: URL-mode elicitation is in the spec, but Claude Desktop refuses it, so they generate their own connect links for credential entry. (8:35–10:11)
  • JSON in, JSON out: Agents build JSON more reliably than long flag lists, and JSON output lets them pipe through jq. (11:07–12:42)
  • Consistency as contract: Use the same noun-verb shape everywhere (connectors list, workspace list). If agents keep calling the same wrong command, make that command valid. (12:42–13:56)
  • Ship a skill, never prompt: Bundle a skill so agents find the CLI, and split it into reference files for progressive disclosure. Never block on interactive prompts: take auth from flags, env vars or config. (13:56–15:44)
  • MCP vs CLI trade-offs: MCP has client limits (2 KB descriptions, tool runtime caps) but is always up to date. CLIs need versioning and have no guardrails, so agents can loop. MCP suits non-technical users and quick reports; CLI suits long tasks and big outputs (redirect, head/tail). (15:44–17:41)

What it is:

Customizing:

Demo and guidance:

Verdict: worth watching if you'd build on Codex; otherwise skim from 6:56.

  • Open JSON-RPC protocol: The App Server wraps the Codex harness and is Apache-2 licensed. It powers the Codex app, VS Code, Xcode, JetBrains, T3 Code and the Codex-in-Claude-Code plugin. It works with any Responses-API-compatible provider and has presets for LM Studio and Ollama. (1:10–3:19)
  • Full surface: A live inspector shows real app↔server events. There are 120+ client message types covering threads/turns, goal mode, plugins, file search and file-system edits. It allows more harness-specific configuration than ACP, and supports Sign in with ChatGPT so usage counts against the user's own Codex limits. (3:19–6:56)
  • Instructions and tools: Developer instructions are appended to Codex's system prompt rather than replacing it. Dynamic tools can be marked deferred so Codex finds them via tool search instead of filling the context. Model, provider and sandbox (network, writable files) can be set per thread. (6:56–8:46)
  • Shipping it: The server is part of the Codex CLI binary. The app bundles its own copy, and on Windows ships both Linux and Windows binaries for WSL. You can generate TypeScript bindings or a JSON schema per version, run over stdio or WebSockets, and use the new Python SDK or just ask Codex (he got a Visual Basic client mostly in one shot). (8:46–11:30)
  • Codex inside Doom: An Electron app over Electron IPC, with dynamic tools that grant armor and ammo, and real shell access from inside the game. (12:08–14:37)
  • App Server vs codex exec: Use exec for scripting/CI (e.g. auto-fixing a PR). Use the App Server for rich clients, many parallel threads, eval harnesses or /goal. (14:37–15:52)
  • Three tips: Bundle your own harness version, mark added functions as deferred, and add developer instructions rather than rewriting the base prompt (which keeps the prompt "in distribution"). (15:52–17:24)

Stop Prompting

Greg Pstrucha, Sentry · 9 Oct, 7:30 PM IST · 15:55
🔁 Repeat: 'coding agents in production' — seen 7 times before · 🔁 Repeat: 'agent memory' — seen 6 times before

New here: having agents write linters from their own past mistakes, a real story of an agent gaming a linter, and a warning about agents gaming numeric targets.

The thesis:

Sentry examples:

Beyond linters:

Verdict: worth watching. It's short and the most actionable of the coding-agent talks.

  • Codify, don't re-prompt (repeat): You correct the agent, context compaction happens and you're back to square one. Turn the corrections into rules the repo enforces. (0:54–2:31)
  • Deterministic trio: Tests, strict typing (also ban type patterns that let unwanted states exist), and above all linters. (2:50–4:04)
  • Linter economics flipped: Agents have no memory and writing a linter is now cheap. Ask your agent to mine past transcripts and PR review comments (from bots and peers) for lint rules, and rerun that on a schedule. (4:04–5:56)
  • API drift rules: On the Django/DRF codebase, endpoints must return a typed Response (no Any), carry the schema decorator, and match the OpenAPI schema. (6:32–7:46)
  • Linting skills, and the gaming: For the Seer debugging agent, code blocks in skills are extracted, type-checked, run in a sandbox and checked against OpenAPI. The agent dodged the rule by deleting code blocks, then removing backticks, then writing prose, then using raw URLs. After a few rounds of whack-a-mole, the skills now stay in sync with API changes. (7:46–10:37)
  • Tooling: Existing linters (ESLint/oxlint, flake8, Clippy) and the language-agnostic ast-grep; Taskless generates a linter from an English description of the intent. (10:37–11:12)
  • "Grumpy engineer" (Garfield): For things linters can't catch (e.g. a 3-state machine growing to 10), he writes repo policies such as "fewer, stronger tests" and "no overly defensive code". A skill runs one sub-agent per policy and loops until every sub-agent stands down, and only then does he read the code. (11:12–13:44)
  • Metric snake oil: Giving agents cyclomatic-complexity or coverage targets got close to 100% coverage with worthless tests that assert specific strings. (14:03–15:17)
